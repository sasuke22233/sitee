## 2. Иерархия ключей

```
Master Key (MK)                — HSM / оффлайн, церемония генерации, ротация 24 мес
  └── KEK[domain]              — Vault Transit / KMS, ротация 90 дней, версионируется
        └── DEK[object]        — генерируется crypto-core, ротация 365 дней (re-encrypt фоном)
              └── данные       — AES-256-GCM ciphertext в PostgreSQL / S3
```

* `domain` ∈ {`msg`, `product_stock`, `pii`, `wallet`, `2fa`, `dispute`, `backup`, `audit`}.
* DEK никогда не хранится в БД в открытом виде — только `wrapped_dek = AES-GCM(KEK, DEK)`.
* Расшифровка DEK выполняется **только в crypto-core**; Go получает plaintext в память на время
  операции, запрещено логировать и сериализовать.
* `key_id` в envelope позволяет ротацию без массового re-encrypt (ленивая миграция при записи).

**Процедура ротации KEK:** 1) сгенерировать новую версию; 2) новые записи — на новую версию;
3) фоновая задача re-wrap DEK (plaintext DEK не покидает crypto-core); 4) старая версия — в
`decommissioned` после полной миграции; 5) отчёт и запись в аудит.

**Процедура при компрометации KEK (ceremony):** изоляция сервиса, генерация нового MK/KEK,
re-wrap всех DEK, re-encrypt критичных доменов (`wallet`, `2fa`), уведомление пользователей
о необходимости перенастройки 2FA, отзыв сессий, постмортем.

## 3. Шифрование данных в БД (at-rest)

Формат envelope — `docs/architecture.md` §4. Применения:

| Объект | Поля в ciphertext | AAD | Примечание |
|---|---|---|---|
| Сообщения чатов | `body_ct`, `attachment_meta_ct` | `msg:<chat_id>:<seq>` | E2EE-чаты: сервер не может расшифровать (нет DEK клиента) |
| Сток товаров | `payload_ct` (ключ/файл-ссылка/учётка) | `stock:<product_id>:<item_id>` | выдача атомарна, чтение только при выдаче заказа |
| ПД пользователей | `email_ct`, `phone_ct`, `geo_ct` | `pii:<user_id>` | для поиска — слепой индекс `HMAC(idx_key, lower(email))` |
| TOTP-секреты | `secret_ct` ×2 (вход/операции) | `2fa:<user_id>:<factor>` | показ секрета только при настройке, далее — never |
| Приватные ключи Solana | `key_ct` | `wallet:<account_id>` | только в crypto-core/HSM |
| Вложения споров | S3-объект шифруется DEK `dispute` | `dispute:<id>:<file>` | EXIF-стриппинг до шифрования |

**Слепые индексы (blind index).** Для поиска по email/нику/адресу кошелька:
`blind = HMAC-SHA256(K_idx, normalize(value))`, `K_idx` — отдельный KEK-домен. В БД хранится
только blind-индекс (unique), что даёт точный поиск без раскрытия значения.

**Шифрование диска и бэкапов:** LUKS/dm-crypt на нодах + SSE-S3, бэкапы — отдельным ключом
(`backup`-домен, age/AES-256-GCM), хранение в другом регионе, проверка восстановления
ежеквартально.

## 4. E2EE мессенджера (приватные чаты и споры)

Упрощённая, но криптографически корректная схема на базе Signal-подхода.

### 4.1 Ключи устройств
Каждое устройство клиента генерирует и хранит **локально**:
* `IK` — identity key pair X25519 (длительный) + `ISK_ed` Ed25519 для подписи пакетов;
* `SPK` — signed prekey X25519, подписан `ISK_ed`, ротация 30 дней;
* `OPK[1..N]` — one-time prekeys X25519 (пул ≥ 20, пополнение при < 5);
* `SK_bk` — backup-ключ (опционально, экспортируется пользователем в зашифрованном виде).

Сервер хранит `identity_pub`, `signed_prekey{pub,sig,ts}`, `one_time_prekeys[]` — **только
публичные части**. Приватные ключи не покидают устройство (в TMA — память + secure storage,
`sessionStorage` запрещён).

### 4.2 Начало сессии (X3DH-lite)
```
A хочет писать B:
  1. A запрашивает у сервера пакет B: IK_B, SPK_B, OPK_B (одноразовый, сервер помечает израсходованным)
  2. A генерирует эфемерный EK_A (X25519)
  3. DH:  d1 = DH(IK_A, SPK_B); d2 = DH(EK_A, IK_B); d3 = DH(EK_A, SPK_B); d4 = DH(EK_A, OPK_B)
  4. SK_root = HKDF-SHA256(salt=0, IKM = d1‖d2‖d3‖d4, info="SITEE-X3DH-v1")
  5. A шифрует первое сообщение ключом, выведенным из SK_root, и отправляет
     {ephemeral_pub: EK_A.pub, used_opk_id, ciphertext}
  6. B восстанавливает SK_root симметрично; стороны помечают сессию установленной
```
Аутентичность: клиент сверяет `identity_pub` собеседника по safety-number
(`SHA-256(IK_A‖IK_B)` → 8 групп по 5 цифр) — показ в UI «Проверить код безопасности».

### 4.3 Рэтчет (Double Ratchet, упрощённый)
```
RK (root key) → DH-рэтчет при смене устройства/переустановке
              → симметрический рэтчет на направление:
CK_send = HKDF(CK_send_prev, 0x01) ; CK_recv = HKDF(CK_recv_prev, 0x02)
MK      = HKDF(CK, 0x03)[0..32]     — одноразовый ключ сообщения, затирается после использования
```
* Шифрование: `AES-256-GCM(MK, plaintext, AAD = chat_id‖seq‖sender_device_id‖protocol_version)`;
* Пропущенные сообщения: клиент хранит `MK` для `seq` в окне ≤ 100 (за пределами — «сообщение
  недоступно, обновите сессию»);
* Forward secrecy: компрометация текущего `CK` не раскрывает прошлые сообщения (ключи удалены);
* Post-compromise security: DH-рэтчет при смене устройства восстанавливает защищённость;
* Сервер видит только `ciphertext`, `sender_key_id`, `seq`, метаданные времени/размера.

### 4.4 Группы и каналы
Для групп — **sender-keys** (модель Signal/WhatsApp): каждый участник рассылает свой
`sender_chain_key` остальным через 1:1 E2EE-сессию; сообщения шифруются собственным ключом
отправителя (экономия на шифровании). Серверная расшифровка невозможна. Для каналов —
подпись Ed25519 автора + опциональное шифрование только для закрытых каналов.

### 4.5 Служебные чаты (`shop_support`, `order`)
По ТЗ (FR-MSG-03/05) такие чаты шифруются **на сервере** (envelope, домен `msg`), а не E2EE —
чтобы админ магазина мог отвечать с любого устройства, а арбитр/модератор имел доступ по
процедуре. Клиент может запросить режим «E2EE с админом» — тогда история недоступна арбитражу,
и в UI показывается явный дисклеймер («спор по такому чату рассматривается без доступа к
переписке»).

### 4.6 Процедура доступа модерации/арбитра к server-encrypted чатам
1. Основание: открытый спор или жалоба с принятым в работу ticket;
2. Запрос `decrypt` в crypto-core с `purpose=arbitration`, `ticket_id`, `dispute_id`;
3. Одобрение вторым привилегированным пользователем (4-глаза) для чужих магазинов;
4. crypto-core возвращает plaintext **только в рамках сессии арбитра**, с водяным знаком
   (`actor_id` + `ts`) в выгрузке;
5. Запись в неизменяемый аудит: кто, когда, какие `message_id`, по какому основанию;
6. Автоотзыв доступа по закрытию спора + TTL 72 ч.

## 5. Двойной 2FA (детали реализации)

### 5.1 Параметры
* RFC 6238: HMAC-SHA1, `period=30`, `digits=6`, секрет 20 байт (160 бит) base32 (RFC 4648, без padding);
* окно проверки: `t ± 1` (т.е. 90 с) — с обязательным анти-replay-журналом использованных
  `(user_id, factor, code_hash)` TTL 120 с;
* provisioning URI: `otpauth://totp/SITEE%20(<label>):<email>?secret=<b32>&issuer=SITEE&algorithm=SHA1&digits=6&period=30`,
  где `label ∈ {вход, операции}`; QR генерируется на клиенте (меньше утечек) или сервером (SVG).

### 5.2 Активация
1. Генерация секрета (crypto-core, crypto/rand) → хранение в ciphertext (домен `2fa`);
2. Пользователь вводит **два подряд** верных кода (проверка синхронизации часов);
3. Выдача 10 backup-кодов (показ один раз, хранятся HMAC-SHA256 с солью);
4. Запись в аудит `2fa.enrolled{factor}`; рассылка уведомления во все сессии.

### 5.3 Политика применения
| Операция | Фактор 1 | Фактор 2 |
|---|---|---|
| Вход с нового устройства/IP/страны | ✅ | — |
| Вход с доверенного устройства (≤ 30 дней) | — (по настройке) | — |
| Вход в админ-панель | ✅ | ✅ |
| Вывод средств, обмен, оплата аренды | — | ✅ |
| Покупка ≥ порога (1000 ⭐ / 5 SOL) | — | ✅ |
| Смена пароля/email/2FA, передача магазина | — | ✅ |
| Создание магазина, публикация первого товара | — | ✅ |
| Открытие/ответ в споре, решение арбитра | — | ✅ |
| Деструктивные действия админа (бан, рефанд, sweep) | — | ✅ (+4-глаза для финансов) |

### 5.4 Атаки и защиты
| Атака | Защита |
|---|---|
| Перебор 6-значного кода | 1 попытка/5 с на аккаунт, лок 3/10 неудач, капча, IP-лимит 10/мин |
| Replay кода в пределах окна | Журнал использованных кодов (TTL 120 с) |
| Фишинг прокси (AiTM) | Короткий TTL access-токена (15 мин), привязка сессии к device-fingerprint, запрет переноса сессии между IP-геозонами без фактора 2 |
| SIM/Telegram-перехват | 2FA не зависит от SMS; коды подтверждения — только в Telegram-боте с проверкой `auth_date ≤ 5 мин` |
| Кража backup-кодов | Одноразовость, HMAC-хранение, уведомление об использовании, принудительная регенерация после 3 использований |
| Рассинхрон времени | Проверка `t ± 1`, явная ошибка `TOTP_DRIFT` с инструкцией |

## 6. Ключи Solana и подпись транзакций

* Мастер-ключ кошелька площадки `MK_sol` (32 байта) хранится **только** в crypto-core (в проде —
  HSM/PKCS#11); в БД — `wrapped` версия.
* Депозитный адрес пользователя: `path = m/44'/501'/<user_index>'/0'` (ed25519 HD, SLIP-0010);
  приватная часть выводится внутри crypto-core и никогда не возвращается вызывающей стороне —
  наружу отдаётся только **публичный адрес** (base58) и `account_id`.
* Подпись транзакции: `POST /v1/solana/sign {tx_bytes, account_id, purpose, idempotency_key}` →
  crypto-core проверяет `purpose ∈ {withdraw, sweep, fee}`, лимиты (`withdraw ≤ hot_limit`),
  whitelist-адрес получателя, подпись 4-глаза для сумм ≥ порога → возвращает `signature`.
* Горячий кошелёк: лимит баланса (по умолчанию 500 SOL), автоматический sweep в холодный при
  превышении; холодный — оффлайн/multisig (3-из-5), движение только по процедуре.
* Все запросы на подпись логируются (`who, purpose, amount, dest, tx_id, sig_hash`) в аудит.

Подробности модели депозитов/выводов и сверки — `docs/solana.md`.

## 7. Анти-брутфорс (детально)

### 7.1 Счётчики и пороги
| Ключ | Порог | Реакция |
|---|---|---|
| `login:{email}` | 3 неудачи/15 мин | капча |
| `login:{email}` | 5 неудач/15 мин | лок 15 мин + уведомление владельцу |
| `login:{email}` | 15 неудач/24 ч | лок 24 ч + тикет в поддержку |
| `login:{ip}` | 20 неудач/15 мин | лок IP 15 мин + капча для всех с IP |
| `login:{asn}` | 200 неудач/час | challenge-режим для ASN, алерт |
| `login:{fingerprint}` | 10 неудач/час | лок устройства 1 ч |
| `2fa:{user,factor}` | 3/5 неудач | лок фактора 30 мин / 30 мин + поддержка |
| `register:{ip}` | 3/сутки | капча + отложенная активация |
| `password_reset:{email}` | 3/час | лок + уведомление |
| `withdraw:{user}` | 3 неудачных подтверждения | заморозка вывода 24 ч + поддержка |

Экспоненциальная задержка ответа на `login` (constant-time + jitter 200–800 мс после 2 неудач) —
снижение скорости перебора без отказа в обслуживании легитимных пользователей.

### 7.2 Скоринг (Rust `fraud/score`)
Признаки: число неудач, возраст аккаунта, совпадение IP/ASN с ранее забаненными, geo-несоответствие,
VPN/Tor/хостинг-ASN, частота запросов, device-fingerprint-коллизии, поведение мыши/скролла (SHOULD),
breach-статус пароля. Выход: `score 0…1000` и `action ∈ {allow, captcha, delay, deny, ban_ip,
ban_account, manual_review}`. Правила версионируются, все срабатывания логируются.

### 7.3 Honeypot и ловушки
Скрытые поля в форме входа (`website`), невидимые ссылки на «админку» в HTML, фейковые эндпоинты
`/wp-login.php`, `/admin.php` — любое обращение ⇒ пометка клиента как бота и ban на 24 ч.

## 8. Анти-DDoS (эшелонированная защита)

| Эшелон | Уровень | Механизмы |
|---|---|---|
| 1. Провайдер/CDN | L3–L4 | Anycast, scrubbing-центры, SYN-cookies, geo-блок нецелевых стран, Blackhole по подсетям, Magic Transit / Shield Advanced |
| 2. Edge (Cloudflare) | L7 | WAF (OWASP CRS + custom), Bot Fight Mode, JS/TLS-challenge, JA3/JA4-фингерпринт, rate-limiting-правила, кэш статики, «Under Attack Mode» (ручной/авто) |
| 3. nginx | L7 | `limit_req_zone` (IP + URI-группы), `limit_conn`, таймауты (`client_body_timeout 10s`, `send_timeout 10s`), запрет методов кроме GET/POST/PATCH/DELETE, размер тела ≤ 8 МБ, отсечение медленных соединений |
| 4. Приложение (Go) | L7 | Rate-limit-профили через Rust-движок (Redis-счётчики), бюджет нагрузки (shedding): при `inflight > N` — `503 + Retry-After` для неавторизованных, приоритет платежам и WS |
| 5. WebSocket | L7 | Лимиты соединений/сообщений/размера кадра, auth-window 10 с, read/write deadlines, kick slow consumers, изоляция ноды по пользователям |
| 6. Данные | — | Кэш ленты (15 с) и CDN (60 с), typeahead-кэш, отключение тяжёлых фич по фиче-флагу, read-only-режим витрины при атаке на БД |

**Правила nginx (пример)** — `deploy/nginx/sitee.conf`; **профили лимитов** — таблица ниже:

| Профиль | Путь | Лимит |
|---|---|---|
| `public` | `/api/v1/shops*`, `/api/v1/gifts*` | 60 req/min/IP, burst 20 |
| `auth` | `/api/v1/auth/*` | 10 req/min/IP + 5 req/min/email |
| `2fa` | `/api/v1/auth/2fa/*` | 1 req/5 s/user |
| `payment` | `/api/v1/wallet/*`, `/api/v1/orders/*/pay`, `/api/v1/exchange/*` | 10 req/min/user |
| `write` | POST/PATCH остальные | 120 req/min/user |
| `admin` | `/api/v1/admin/*` | 120 req/min/user + IP-allowlist |
| `ws-connect` | `/ws` | 5/min/IP, 10 соединений/user |
| `ws-msg` | кадры | 60 msg/min/user, 64 КБ/кадр |
| `chat-msg` | `POST /chats/{id}/messages` и кадры `msg.send` | 100 msg/min/user в чате, burst 30; после 3 отказов подряд — автоматический мут на 30 мин (`429 RATE_LIMITED`, затем `403 MUTED`) |

Мут и блокировку участника чата выставляет модератор (флаги `muted`/`blocked` у участника); автоматический мут по троттлингу снимается по таймеру, ручной — только вручную.

**План реагирования (runbook):** 1) подтвердить атаку (метрики, источники, вектор);
2) включить challenge/Under Attack; 3) сузить гео-блок; 4) ужесточить лимиты анонимов;
5) отключить тяжёлые фичи (фиче-флаги); 6) при L3/L4 — blackhole подсетей у провайдера;
7) информировать пользователей (канал/баннер); 8) постмортем в течение 48 ч.

## 9. Безопасность приложения (чек-лист)

* **Авторизация**: RBAC + проверка владения ресурсом на каждом хендлере (`shop.admin_user_id == me`),
  запрет массового присвоения полей (явные DTO), `403` без раскрытия существования объекта.
* **Валидация**: строгие DTO, лимиты длин, whitelist типов файлов, проверка MIME по содержимому,
  ограничение JSON-вложенности и размера тела.
* **Инъекции**: только параметризованные запросы; никаких string-concat в SQL; для FTS — нормализация
  и экранирование; команды ОС не вызываются никогда.
* **XSS**: серверный рендер не используется для пользовательского HTML; клиент — sanitize
  (allowlist тегов), CSP `default-src 'self'; script-src 'self' https://telegram.org
  'nonce-…'; img-src 'self' data: blob: https:; connect-src 'self' wss: https:; frame-ancestors
  'self' https://web.telegram.org https://t.me; object-src 'none'; base-uri 'none'`.
* **CSRF**: для cookie-сессий — `SameSite=Lax` + CSRF-токен на мутирующих методах; для TMA —
  проверка `init_data` HMAC и `Authorization: Bearer`.
* **SSRF**: исходящие HTTP-запросы (webhook'и, превью ссылок) — только через egress-прокси с
  запретом приватных диапазонов и metadata-endpoint'ов.
* **Секреты**: никаких ключей в клиентском бандле; проверка gitleaks в CI и pre-commit;
  `.env` в gitignore; отдельные KEK на окружение.
* **Заголовки**: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer`, `Permissions-Policy: (минимум)`, `Cross-Origin-Opener-Policy`,
  `Cross-Origin-Resource-Policy: same-site`.
* **Логирование**: маскирование (`maskPII`), запрет логирования ciphertext-plaintext, кодов 2FA,
  приватных ключей, полных адресов кошельков.
* **Зависимости**: Go — только stdlib в MVP (далее `govulncheck`), Rust — std-only MVP (далее
  `cargo-audit`), фронт — SRI для `telegram-web-app.js`, `npm audit` в CI.
* **Тесты безопасности**: SAST (semgrep), DAST (ZAP baseline) в CI, пентест перед запуском и далее
  ежегодно, bug-bounty (этап 2).

## 10. Неизменяемый аудит-лог

audit_log(id, ts, actor_id, actor_role, action, object_type, object_id,
          before_json, after_json, reason, ip, ip_geo, user_agent,
          totp_factor_verified, prev_hash, record_hash)
record_hash = SHA-256(prev_hash ‖ canonical_json(record без record_hash))

* Запись только INSERT; UPDATE/DELETE запрещены на уровне роли БД (`REVOKE`), плюс триггер;
* Ежесуточно — якорь хэша головы цепи в публичный канал/блокчейн (SHOULD: запись в Solana memo),

* Хранение ≥ 5 лет, WORM-хранилище для архива;
* Обязательные события: вход/выход/неудачи, 2FA, смена ПД, создание/изменение магазина, аренда,

  изменения ключей, санкции, жалобы и модерация.

## 11. Приватность и соответствие

* Минимизация: собираем только email/telegram, страну, город, платёжные идентификаторы;
* Право на доступ/экспорт: выгрузка всех данных пользователя в JSON (30 дней по запросу);
* Право на удаление: soft-delete 30 дней → анонимизация ПД (email → hash, geo → country only,
  аватар/имя → удалены), финансовые записи и аудит сохраняются обезличенными (обязательство);
* Хранение ПД: регион по выбору (ЕС/РФ), реестр обработки, DPA с провайдерами;
* Cookie/согласия: баннер с категориями, отказ от аналитики без потери функциональности;
* Возрастное ограничение 18+ (подтверждение при регистрации), запрет категорий 18+ по юрисдикциям.
