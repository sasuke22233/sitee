**Принцип:** весь клиентский трафик идёт через один Go-периметр (API + WS). Rust-ядро — внутренняя
служба, недоступная извне, вызывается только Go-сервисами по приватной сети/mTLS или UNIX-сокету.

## 2. Распределение Go / Rust (обоснование)

### 2.1 Go (`backend/`)
* HTTP/REST и WebSocket (огромная экосистема, дешёвые горутины → 10k+ WS-соединений на ноду);
* доменная логика: магазины, аренда, каталог, заказы, статус-машина, споры, отзывы, подарки;
* ledger двойной записи и идемпотентность (важна читаемость и строгая типизация транзакций);
* интеграции: Telegram Bot/Stars API, Solana RPC (чтение/сканирование), S3, SMTP;
* админка, RBAC, аудит, worker'ы и таймеры.

### 2.2 Rust (`crypto-core/`)
* **всё криптографическое**: AES-256-GCM envelope encrypt/decrypt, HKDF-SHA256, PBKDF2, HMAC, TOTP;
* **ключи Solana**: генерация, хранение (зашифровано), HD-деривация депозитных адресов,
  сериализация и **Ed25519-подпись** транзакций (закрытый ключ не покидает процесс);
* **rate-limit** (token bucket, sliding window, распределённый через Redis-счётчики);
* **анти-фрод скоринг** (скользящие окна событий, правила, ML-признаки — этап 2);
* причины: предсказуемая латентность без GC, `no_std`-совместимые примитивы, аудируемый код,
  изоляция секретов в отдельном процессе с отдельными правами (меньше поверхность атаки).

### 2.3 Контракт Go ⇄ Rust
Внутренний HTTP/1.1, JSON (в проде — mTLS + service-token; опционально UNIX-socket):

| Метод | Путь | Назначение | Таймаут |
|---|---|---|---|
| POST | `/v1/keys/wrap` | обёрнуть DEK под KEK домена | 100 мс |
| POST | `/v1/keys/unwrap` | снять обёртку (аудит) | 100 мс |
| POST | `/v1/encrypt` | AES-256-GCM: `plaintext+aad → ct‖nonce‖tag` | 200 мс |
| POST | `/v1/decrypt` | обратная операция (аудит, RBAC) | 200 мс |
| POST | `/v1/kdf/hkdf`, `/v1/kdf/pbkdf2` | вывод ключей | 300 мс |
| POST | `/v1/totp/issue`, `/v1/totp/verify` | секреты 2FA (verify — с анти-replay) | 150 мс |
| POST | `/v1/solana/address` | HD-деривация депозитного адреса (base58) | 150 мс |
| POST | `/v1/solana/sign` | подпись транзакции (только из sol-scanner) | 300 мс |
| POST | `/v1/ratelimit/check` | `key, cost → allow, retry_after` | 50 мс |
| POST | `/v1/fraud/score` | `events[] → score, reasons[], action` | 100 мс |
| GET | `/healthz`, `/metrics` | здоровье и метрики | — |

**Fallback:** если `CRYPTO_CORE_URL` не задан или ядро недоступно (circuit-breaker: 5 ошибок/10 с →
open 30 с), Go использует встроенную реализацию на `crypto/aes`, `crypto/cipher`, `crypto/hmac`,
`crypto/sha256`, `crypto/pbkdf2`. Формат ciphertext идентичен (см. §4), поэтому данные переносимы
между реализациями. Событие `crypto_core_down` ⇒ алерт P2, запись в аудит, метрика `crypto_fallback_total`.

    ├── messenger/                # чаты, группы, каналы, сообщения, E2EE-метаданные

Правило зависимостей: `admin` → домены; домены → `ledger`, `store`, `cryptod`, `platform`;
`ledger` не знает о HTTP. Никаких циклов. Каждый модуль имеет свой набор ошибок и свой
набор событий в шину.

## 4. Формат зашифрованных данных (единый для Go и Rust)

```
Envelope v1:
  ┌──────┬────────────┬───────────┬──────────┬───────────────┬──────────┐
  │ 0x01 │ key_id (8) │ nonce (12)│ aad_len  │ ciphertext+tag│  (pad)   │
  └──────┴────────────┴───────────┴──────────┴───────────────┴──────────┘
  · AES-256-GCM, tag 16 байт внутри ciphertext-блока (Go/Rust соглашение)
  · key_id  = идентификатор версии DEK (таблица data_keys)
  · nonce   = 96 бит, случайный (crypto/rand), уникальность на ключ ≤ 2^32 записей
  · aad     = контекст: "<domain>:<object_id>:<version>" — защищает от подмены записей
  · в БД    = base64(envelope) в колонках * ciphertext, либо bytea
```

Домены ключей (`key domains`): `msg` (сообщения чатов), `product_stock` (единицы товаров),
`pii` (email, телефон, адрес), `wallet` (приватные ключи Solana), `2fa` (TOTP-секреты),
`dispute` (вложения споров), `backup` (резервные копии).

## 5. WebSocket-протокол (`/ws`)

**Подключение.** `GET /ws?token=<access>` или первый кадр `hello` с токеном (аутентификация
обязательна в течение 10 с, иначе разрыв `4401`). Поддомен/путь единый для всех типов диалогов.

**Кадры.** Текстовые JSON (в проде — protobuf поверх бинарных кадров). Общая оболочка:

```jsonc
{ "v": 1, "id": "01J9ZK...", "t": "msg.new", "ts": 1760000000123, "d": { /* payload */ } }
```

| Тип `t` | Направление | Назначение |
|---|---|---|
| `hello` / `hello.ok` | C→S / S→C | аутентификация, `last_seq` по чатам, capabilities |
| `ping` / `pong` | обе | heartbeat 25 с, read deadline 60 с |
| `msg.send` / `msg.sent` | C→S / S→C | отправка (клиентский `client_msg_id` → идемпотентность) |
| `msg.new` | S→C | новое сообщение (ciphertext + метаданные) |
| `msg.edit` / `msg.del` | обе | редактирование/удаление |
| `chat.typing` | обе | «печатает…» (троттлинг 1/3 с) |
| `chat.read` | обе | отметки прочитанного |
| `presence` | S→C | онлайн-статус админов магазина |
| `order.status` | S→C | смена статуса заказа |
| `dispute.event` | S→C | шаги спора (открыт/эскалация/решение) |
| `notify` | S→C | системные уведомления |
| `error` | S→C | код + человекочитаемое сообщение |

**Доставка и надёжность.** Каждому сообщению в чате присваивается монотонный `seq`
(per-chat, выдаётся сервером атомарно). Клиент хранит `last_seq`; при reconnect шлёт
`hello{last_seq}` и получает `msg.backfill[]`. Сервер хранит недоставленные сообщения в
Redis-очереди на устройство (TTL 30 сут). Гарантии: at-least-once + идемпотентность по
`(chat_id, seq)` на клиенте.

**Ограничения (анти-DDoS, см. `security.md` §8):** 5 соединений/IP, 10/пользователь,
60 сообщений/мин, кадр ≤ 64 КБ, очередь отправки ≤ 256 кадров, backpressure ⇒ отключение
медленных клиентов (`slow_consumer_kicked`).

**Масштабирование WS.** Несколько нод `siteed-ws`; маршрутизация пользователя на ноду —
consistent hashing по `user_id` на nginx-уровне (или Redis pub/sub fan-out между нодами:
каждая нода публикует `msg.new` в канал `chat:<id>`, остальные доставляют своим клиентам).

## 6. Данные и консистентность

* **PostgreSQL 16** — источник истины: пользователи, магазины, товары, заказы, ledger, споры,
  отзывы, метаданные сообщений. Транзакционность заказа и ledger — в одной БД-транзакции.
* **Outbox** — таблица `events` пишется в той же транзакции, что и доменное изменение;
  релэй (worker) публикует в Redis Streams/NATS; потребители идемпотентны (`event_id`).
* **Redis 7** — кэш ленты (15 с), rate-limit-счётчики, presence, typing, очереди WS,
  сессии-джойны, распределённые блоки (Redlock — только для неответственных задач).
* **S3/MinIO** — обложки, аватары, медиа подарков, файлы товаров (шифрование SSE +
  приложение-уровневое для приватных), подписанные URL.
* **Vault/KMS** — KEK и мастер-ключи, Transit-операции (в MVP — файл-хранилище KEK с
  правами 0400 и отдельным пользователем, помечено как «dev only» в конфиге).

**Инварианты ledger** (проверяются ежеминутно и при каждой записи):
1. `Σ debits == Σ credits` по всем счетам (в разрезе валюты);
2. баланс любого счёта ≥ 0 (кроме служебных `escrow:*` и `platform:*`);
3. `Σ escrow(активные заказы) == Σ замороженных средств по заказам`;
4. `hot_wallet_balance + Σ user_balances == Σ deposits − Σ withdrawals` (сверка с блокчейном).
Нарушение любого инварианта ⇒ P1-алерт и автоматическая блокировка выводов.

## 10. Отказоустойчивость и деградация

| Отказ | Поведение системы |
|---|---|
| crypto-core недоступен | Go-fallback на `crypto/*` (тот же формат), алерт P2, метрика; подпись Solana **запрещена** (операции вывода ставятся в очередь) |
| Redis недоступен | Кэш bypass, rate-limit переходит в локальный (консервативные лимиты), WS fan-out только в пределах ноды, алерт P2 |
| PostgreSQL primary упал | Failover на реплику (Patroni/repmgr), API в режим read-only для витрины, платежи приостанавливаются → операции ставятся в очередь с идемпотентным ключом |
| Solana RPC деградирует | Переключение на резервный RPC, зачисления по подтверждениям, ручная очередь при рассинхроне |
| Telegram API недоступен | Оффлайн-доставка в очередь, вход по email+2FA остаётся рабочим |
| DDoS L7 | Challenge-режим, ужесточение лимитов для анонимов, отключение «тяжёлых» фич (typeahead-поиск, персонализация) по фиче-флагу |
