## 1. Цели и границы проекта

### 1.1 Цель
Построить защищённый маркетплейс цифровых товаров, в котором:

* магазины («шопы») **привязаны к администратору магазина** и работают по модели **ежемесячной аренды**;
* **любой диалог покупателя открывается с админом** (владельцем/оператором магазина), а не с анонимным продавцом;
* все денежные потоки исполняются в **SOL** (внутренний кастодиальный баланс) и/или **звёздах**;
* переписка передаётся по **WSS** и хранится в БД **в зашифрованном виде (AES-256)**, а приватные чаты — с **E2EE**;
* платформа выдерживает целенаправленные атаки: **брутфорс, credential stuffing, DDoS L3–L7**.

### 1.2 Бизнес-модель (источники дохода)
| # | Источник | Механика |
|---|---|---|
| 1 | **Аренда магазина** | Ежемесячная абонентская плата по тарифам (SOL или звёзды). Премиум-тариф даёт «коронку» и приоритет в ленте |
| 2 | Комиссия с продаж | % с каждого завершённого заказа (настраивается по тарифу аренды) |
| 3 | Обменник | Спред/комиссия на обмен Stars ⇄ SOL, комиссия на вывод |
| 4 | Подарки | Наценка на цифровые подарки, «буст» магазина подарками |
| 5 | Продвижение | Разовые пакеты поднятия в ленте (без изменения тарифа) |

### 1.3 В границах (In scope)
Регистрация/вход, геопрофиль (страна+город), двойной 2FA, витрина и поиск магазинов, карточка
магазина, каталог цифровых товаров с автовыдачей, корзина/заказ/эскроу, статусы заказа, мессенджер
(личные чаты, группы, каналы) с шифрованием, споры с маскировкой и арбитражем, звёзды, каталог
подарков и их покупка, обменник, отзывы и рейтинг, админ-панель, кастодиальные SOL-кошельки
(депозит/вывод), анти-брутфорс и анти-DDoS, деплой.

### 1.4 Вне границ (Out of scope) на MVP
Физические товары и логистика; фиатные эквайринги (карты/СБП) — только SOL и Stars;
некастодиальный on-chain эскроу (описан как развитие в `docs/solana.md`, §9); мобильные нативные
приложения (только TMA); KYC-провайдер (интерфейс заложен, интеграция — этап 4);
мультивалютность кроме SOL/USDC/Stars.

### 1.5 Юридические оговорки
Продажа цифровых товаров регулируется юрисдикцией продавца и покупателя. Площадка:
(а) хранит страну/город пользователя и применяет **геоблокировки категорий** по чёрным спискам
юрисдикций; (б) ведёт журнал аудита всех операций; (в) имеет процедуру takedown по жалобе
правообладателя; (г) не является кастодианом в смысле банковской лицензии — средства учитываются
как предоплата/эскроу-обязательство площадки (требуется юридическая экспертиза до запуска,
см. §11, риск R1).

## 2. Термины и роли

### 2.1 Термины
| Термин | Определение |
|---|---|
| **Шоп / магазин (shop)** | Страница продавца цифровых товаров: обложка, название, описание, рейтинг, каталог, чат |
| **Админ магазина (shop admin)** | Учётная запись, к которой **жёстко привязан** магазин; владелец аренды и точка контакта в диалогах |
| **Коронка (crown)** | Визуальный маркер премиум-магазина в углу карточки: активный премиум-тариф аренды и/или топ-рейтинг |
| **Аренда (rent)** | Ежемесячная подписка на тариф магазина; неоплата ⇒ заморозка витрины и снятие коронки |
| **Цифровой товар (product)** | Товар с немедленной электронной выдачей: ключ, лицензия, файл, аккаунт, подписка, услуга-код |
| **Автовыдача (auto-delivery)** | Выдача единицы товара из зашифрованного стока сразу после подтверждения оплаты |
| **Эскроу** | Заморозка средств покупателя на внутреннем ledger до завершения заказа |
| **Спор (dispute)** | Процедура разрешения конфликта по заказу с приглашением админа-арбитра |
| **Маскировка** | Псевдонимизация сторон в споре: участники видят друг друга как `Продавец #A17` / `Покупатель #K92` |
| **Звёзды (Stars, XTR)** | Расчётная единица Telegram Stars; используется для подарков и буста |
| **Подарок (gift)** | Цифровой подарок из каталога площадки: покупается за звёзды или SOL, дарится пользователю/магазину |
| **KEK / DEK** | Key Encryption Key (в KMS/HSM) / Data Encryption Key (на таблицу или чат) — envelope-шифрование |
| **E2EE** | Сквозное шифрование: сервер хранит и передаёт только ciphertext, ключи — на устройствах |

## 3. Общая концепция и пользовательские сценарии

### 3.1 Концепция «всё через админа»
1. Магазин не существует без админа: `shops.admin_user_id` — обязательное внешнее ключевое поле,
   удаление/блокировка админа ⇒ заморозка магазина.
2. Любая кнопка «Написать», «Задать вопрос», «Открыть спор», «Сообщить о проблеме» создаёт или
   открывает диалог, в котором **второй стороной всегда является админ**:
   * вопросы по магазину/товару → админ магазина (и его операторы, если назначены);
   * системные вопросы, споры, апелляции → админ платформы (арбитражная очередь);
   * если у магазина несколько операторов, диалог всё равно принадлежит магазину и виден админу —
     админ является владельцем диалога и может перехватить его в любой момент.
3. Покупатель никогда не видит личные данные админа (только публичный ник магазина, бейдж
   «Админ магазина», рейтинг, время ответа). Админ видит покупателя в рамках заказа; вне заказа —
   только псевдоним и геопрофиль (страна/город), если покупатель не раскрыл себя.

### 3.2 Ключевые сценарии (user stories)
**US-01. Регистрация.** Гость открывает TMA → главная с логотипом, кнопки «Вход» / «Регистрация» →
вводит email или Telegram-аккаунт, пароль, выбирает страну и город → подтверждает код из
Telegram/email → попадает на экран настройки **первого** TOTP-фактора (QR для Google Authenticator)
→ затем **второго** TOTP-фактора (отдельный секрет для финансовых операций) → сохраняет backup-коды
→ **автоматический переход на главную страницу с магазинами** (лента, слева логотип, поле
«Поиск по магазинам» и кнопка «Найти»).

**US-02. Покупка.** Покупатель находит магазин → карточка (обложка, название, рейтинг, коронка) →
товар → «Купить» → выбор оплаты (SOL-баланс / Stars / пополнить) → подтверждение **вторым**
TOTP-кодом для сумм ≥ порога → эскроу → автовыдача цифрового товара → чат с админом магазина →
подтверждение получения (или автотаймер 72 ч) → отзыв → раскрытие эскроу продавцу.

**US-03. Спор.** Товар не работает → «Открыть спор» в чате заказа → выбор причины, описание,
вложения → чат спора с **маскировкой** сторон → продавец отвечает → эскалация «Пригласить админа»
→ арбитр входит в спор, видит реальные ID и всю переписку → решение: возврат / частичный возврат /
отклонение → исполнение через ledger, запись в аудит.

**US-04. Аренда магазина.** Продавец регистрируется → «Создать магазин» → выбор тарифа
(Starter / Pro / Crown) → оплата за месяц в SOL или звёздах → магазин появляется в ленте,
на Crown — коронка и приоритет → за 5/3/1 день до окончания — напоминания → автопродление при
включённом флаге → при неоплате: grace 72 ч (витрина помечена «аренда истекает»), затем заморозка
(магазин скрыт из ленты, заказы на выдаче завершаются, чаты доступны на чтение).

**US-05. Подарки.** Пользователь в профиле или в магазине → «Подарки» → каталог (админ добавляет
подарки через админ-панель: название, редкость, цена в Stars и/или SOL, медиа) → покупка за звёзды
или SOL → дарит магазину (буст рейтинга/позиции) или другому пользователю → получатель видит
подарок в профиле, отправитель — в истории.

## 4. Функциональные требования

Обозначения: **MUST** — обязательно к MVP, **SHOULD** — желательно в MVP, **MAY** — этап 2+.
Каждое требование имеет ID для трассировки в тестах (`docs/acceptance.md`).

### 4.1 Вход, регистрация, логотип, главная страница

**FR-AUTH-01 (MUST).** Главная страница до авторизации содержит: логотип SITEE (SVG, светлая и
тёмная темы), название, короткое описание, кнопки **«Вход»** и **«Регистрация»**, ссылки
«Условия», «Политика конфиденциальности», селектор языка (RU/EN), переключатель темы.
Макет — по центру, мобильный-first, высота ≤ 100dvh без скролла на 360×640.

**FR-AUTH-02 (MUST).** Регистрация по email+пароль **или** по Telegram-аккаунту
(`AuthWidget`/`web_app_init_data` с проверкой HMAC-подписи_bot-токена_). Поля: email/telegram,
пароль, подтверждение пароля, страна, город, согласие с условиями (18+), опционально реферальный код.

**FR-AUTH-03 (MUST).** Валидация пароля: ≥ 12 символов, ≥ 3 классов символов, проверка по списку
10 000 самых частых паролей (локальный bloom-фильтр), запрет совпадения с email/ником.
Хэширование — **Argon2id** (m=64 MiB, t=3, p=4, salt 16 B); в Go-MVP допустим PBKDF2-HMAC-SHA256
(210 000 итераций) как fallback с флагом миграции на Argon2id при первом входе.

**FR-AUTH-04 (MUST).** Подтверждение контакта: 6-значный код в Telegram-бот (или email), TTL 10 мин,
лимит 5 отправок/час, 3 попытки ввода.

**FR-AUTH-05 (MUST).** После успешной регистрации и настройки обоих 2FA-факторов —
**автоматический переход на главную страницу с магазинами** (без промежуточных экранов и кликов).

**FR-AUTH-06 (MUST).** Вход: email/ник + пароль → **фактор 1 (TOTP)** → сессия. Для привилегированных
ролей и чувствительных операций — **фактор 2 (TOTP)** (§4.3).

**FR-AUTH-07 (MUST).** Сессии: access-token (JWT, EdDSA/Ed25519, TTL 15 мин) + refresh-token
(TTL 30 сут, ротация, reuse-detection ⇒ отзыв всей семьи токенов). Хранение refresh — httpOnly +
Secure + SameSite=Lax cookie в web-режиме; в TMA — secure storage клиента.

**FR-AUTH-08 (MUST).** Выход: «завершить эту сессию» / «завершить все сессии» (список устройств:
IP-geo, UA, дата, последняя активность, отзыв).

**FR-AUTH-09 (SHOULD).** Восстановление пароля: только через подтверждённый Telegram + **фактор 2**;
при утере обоих факторов — заявка в поддержку с ручной верификацией (SLA 24 ч), сброс невозможен
автоматически (осознанное ужесточение против account takeover).

**FR-AUTH-10 (MUST).** Логотип: единый бренд-набор (SVG + PNG 512/192, favicon, иконка TMA),
используется в шапке ленты, на странице входа, в шапке чатов и в уведомлениях.

### 4.2 Выбор страны и города

**FR-GEO-01 (MUST).** При регистрации обязательны **страна** и **город** (двухуровневый селектор:
страна → город; поиск по названию; для стран без справочника городов — свободный ввод).

**FR-GEO-02 (MUST).** Справочник: ISO 3166-1 alpha-2 для стран, собственный справочник городов
(`cities(id, country_code, name_ru, name_en, population, tz)`), загрузка из seed-файла,
обновление через админку. По умолчанию — автоопределение по `Accept-Language` и IP-geo
(MaxMind GeoLite2 City), пользователь может переопределить вручную (значение пользователя всегда
приоритетнее автоопределения).

**FR-GEO-03 (MUST).** Гео влияет на: (а) порядок ленты («магазины рядом» — буст +0…15 % к скору);
(б) валюту отображения; (в) язык интерфейса; (г) **геоблокировки категорий/товаров** по
юрисдикциям (чёрный список настраивается в админке); (д) анти-фрод-сигналы (несовпадение
IP-geo и профиля ⇒ риск-балл).

**FR-GEO-04 (SHOULD).** Изменение страны/города в профиле: не чаще 1 раза в 30 суток, с подтверждением
фактором 2 и записью в аудит (анти-фрод: «миграция» в льготную юрисдикцию).

**FR-GEO-05 (MUST).** Страна и город пользователя **не передаются** другой стороне в чатах и спорах
без явного согласия пользователя (privacy-by-default); продавец видит агрегат «страна + часовой пояс»
только по активному заказу.

### 4.3 Двойной 2FA Google

**FR-2FA-01 (MUST).** Реализованы **два независимых TOTP-фактора** по RFC 6238 (Google Authenticator
совместим): SHA-1, 30-секундный шаг, 6 цифр, секрет 160 бит base32.

| | Фактор 1 — «Вход» | Фактор 2 — «Операции» |
|---|---|---|
| Назначение | вход в аккаунт, новые устройства | деньги и привилегии |
| Где требуется | каждый вход с нового устройства/IP; вход из новой страны | вывод средств, оплата аренды, смена пароля/почты, покупка ≥ порога, открытие и ответ в споре, создание магазина, действия админа/модератора/арбитра, вход в админ-панель |
| Секрет | отдельный, `totp_secret_login` | отдельный, `totp_secret_ops` |
| OK-окно | ±1 шаг (30 с) | ±1 шаг, с защитой от replay (jti использованных кодов 90 с) |
| Лок | 5 неверных ⇒ 15 мин; 15 ⇒ 24 ч + поддержка | 3 неверных ⇒ 30 мин; 10 ⇒ заморозка вывода и поддержка |

**FR-2FA-02 (MUST).** Настройка каждого фактора: показ QR (`otpauth://totp/SITEE:<email>?secret=…&issuer=SITEE&algorithm=SHA1&digits=6&period=30`)
и ручного секрета; активация только после двух подряд верных кодов (защита от рассинхрона часов);
отдельные метки в Google Authenticator: `SITEE (вход)` и `SITEE (операции)`.

**FR-2FA-03 (MUST).** Backup-коды: по 10 одноразовых кодов на каждый фактор (формат `XXXXX-XXXXX`,
хранятся как HMAC, однократное использование). Сгенерировать заново — только с подтверждением
действующим кодом фактора 2.

**FR-2FA-04 (MUST).** Обязательность: фактор 1 — для всех; фактор 2 — обязателен для продавца
(создание магазина) и для всех привилегированных ролей. Аккаунт без фактора 2 не может:
пополнять/выводить средства, оплачивать аренду, открывать спор.

**FR-2FA-05 (MUST).** Защита: проверка кода не чаще 1 попытки/5 с на аккаунт и 10/мин на IP;
код, уже принятый один раз, не принимается повторно (анти-replay); все неудачи пишутся в
`auth_events` и учитываются анти-фрод-движком (Rust).

**FR-2FA-06 (SHOULD).** Дополнительные каналы (этап 2): WebAuthn/passkey как третий фактор,
push-подтверждение в Telegram-бот («Подтвердить/Отклонить»), аппаратный ключ для супер-админа.

**FR-2FA-07 (MUST).** Смена устройства: старый фактор отзывается только после подтверждения новым
кодом + кода из Telegram; событие рассылается во все активные сессии («Если это были не вы —
смените пароль»).

### 4.4 Лента магазинов и поиск

**FR-FEED-01 (MUST).** Главная (после входа): шапка — **слева логотип**, справа иконки
уведомлений и профиля; ниже — поле **«Поиск по магазинам»** и кнопка **«Найти»**; далее —
**лента магазинов** в виде **сетки карточек** (2 колонки на мобильном, 3–4 на планшете/десктопе,
`grid`, gap 12 px, infinite scroll + «Показать ещё»).

**FR-FEED-02 (MUST).** Карточка магазина содержит: **обложку** (16:9, lazy-load, AVIF/WebP,
placeholder-блюр), **название**, **рейтинг** (звёзды 0–5 с точностью 0.1 + число отзывов),
**коронку в углу** (правый верхний угол, только у premium/verified), дополнительно: страна+город,
число продаж, бейдж «Отвечает ~N мин», метка «Аренда истекает» (если применимо).

**FR-FEED-03 (MUST).** Поиск: по названию, нику, описанию, категориям и товарам магазина.
Полнотекст (PostgreSQL FTS + `pg_trgm` для опечаток, в проде — опционально Meilisearch/Typesense).
Кнопка «Найти» и Enter равнозначны; пустой запрос ⇒ лента по умолчанию; история последних
10 запросов; подсказки (typeahead, ≥ 3 символов, дебаунс 250 мс, кэш 60 с).

**FR-FEED-04 (MUST).** Фильтры и сортировки: страна/город, категория, ценовой диапазон (SOL),
рейтинг ≥ N, «только с коронкой», «отвечает быстро», «новинки». Сортировки: «Рекомендуемые»
(скоринг §FR-FEED-05), «Рейтинг», «Продажи», «Новые», «Цена товаров». Фильтры сохраняются в URL
и в профиле пользователя как «Мои фильтры».

**FR-FEED-05 (MUST).** Скоринг ленты (детерминированный, объяснимый, логируется):
```
score = 0.30*rating_bayes + 0.20*sales_log + 0.15*recency
      + 0.15*rent_tier_boost + 0.10*geo_boost + 0.05*response_speed
      + 0.05*gift_boost − 0.20*complaint_penalty − 0.30*dispute_loss_penalty
```
`rent_tier_boost`: Starter 0, Pro 0.5, Crown 1.0. Запрещено влияние платного продвижения на
отображаемый рейтинг (маркировка «продвинуто» для платных слотов, не более 1 слота на 8 карточек).

**FR-FEED-06 (MUST).** Пагинация — курсорная (`cursor`, `limit ≤ 50`), стабильная при изменении
скоринга. Кэш ответа 15 с (ETag), для гостей — кэш CDN 60 с.

**FR-FEED-07 (SHOULD).** Персонализация: категория-аффинити по просмотрам/покупкам, «Продолжить
просмотр», «Похожие магазины». Отключение персонализации в профиле (privacy).

**FR-FEED-08 (MUST).** Страница магазина: обложка, аватар, название, коронка, рейтинг и отзывы,
описание, страна/город, «Админ магазина: @nick» + кнопка **«Написать админу»** (открывает/создаёт
диалог с админом), витрина товаров (категории, поиск по товарам, цена в SOL и Stars),
статистика (продажи, время ответа, % споров), кнопка «Подарить магазину» (§4.10).

### 4.5 Магазин, привязка к админу, аренда и «коронка»

**FR-SHOP-01 (MUST).** Создание магазина доступно пользователю с активным фактором 2 и выбранной
страной/городом. Поля: название (3–40 симв., уникально по `slug`), slug (латиница/цифры/дефис),
описание (≤ 2000), категория (1–3), обложка (≤ 8 МБ, 1600×900, JPEG/WebP/AVIF), аватар,
контакт для покупателей (по умолчанию — чат с админом), часовой пояс, язык поддержки.

**FR-SHOP-02 (MUST).** **Привязка к админу**: `shops.admin_user_id` — обязателен и неизменяем без
процедуры передачи (подтверждение фактором 2 обоих + апрув супер-админа). Один пользователь —
владелец ≤ 3 магазинов (лимит настраивается). Магазин без активного админа ⇒ статус `frozen`.

**FR-SHOP-03 (MUST).** Операторы магазина: админ может назначить до 5 операторов (чат-поддержка,
выдача товара), каждый — с ролью `shop_operator` в рамках магазина. **Все диалоги магазина видны
админу**; админ может перехватить диалог (`takeover`), оператор не может удалить историю.

**FR-SHOP-04 (MUST).** **Аренда**: тарифы хранятся в `shop_rent_plans` и управляются из админки.
Базовая сетка (настраивается):

| Тариф | Цена, мес | Коронка | Слот товаров | Комиссия площадки | Позиция в ленте | Поддержка |
|---|---|---|---|---|---|---|
| Starter | 5 SOL / 500 ⭐ | — | 20 | 7 % | базовая | бот |
| Pro | 19 SOL / 1900 ⭐ | — | 200 | 5 % | +boost 0.5 | чат, 24 ч |
| **Crown** | 49 SOL / 4900 ⭐ | ✅ | 1000 | 3.5 % | +boost 1.0, слот в топ-ленте | чат, 4 ч |
| Enterprise | договорная | ✅ + verified | без лимита | 2.5 % | индивидуальный слот | менеджер |

**FR-SHOP-05 (MUST).** Жизненный цикл аренды: `trial(7 дней, 1 раз на аккаунт)` → `active` →
`expiring_soon (T−5/3/1 день, push + чат-уведомление админу)` → `grace (72 ч после T, витрина с
меткой, новые заказы запрещены)` → `suspended (магазин скрыт из ленты и поиска, чаты read-only,
активные заказы довыводятся)`. Продление: вручную или автопродление (флаг, списание за 24 ч до T,
при недостатке средств — 3 повтора с интервалом 6 ч, затем `grace`).

**FR-SHOP-06 (MUST).** Оплата аренды: SOL-баланс или звёзды; каждое списание — транзакция ledger с
двойной записью и записью в `shop_rent_subscriptions` + `payments`. Возврат при смене тарифа —
пропорционально неиспользованному времени (pro-rata), только по решению админа платформы.

**FR-SHOP-07 (MUST).** **Коронка** отображается, если: тариф `Crown`/`Enterprise` **И** аренда
`active` **И** рейтинг ≥ 4.0 **И** нет активных санкций. Дополнительно бейдж `verified` — по
решению супер-админа (проверенный продавец). Логика — на сервере, клиент лишь рендерит флаги
(`is_crowned`, `is_verified`).

**FR-SHOP-08 (MUST).** Санкции: `warn` (предупреждение, видно в профиле магазина) →
`restrict` (запрет новых товаров, снижение позиции) → `suspend` (скрыт из ленты) →
`ban` (закрыт, средства замораживаются до окончания всех заказов и споров). Все санкции —
только через админку, с причиной, сроком, апелляцией.

**FR-SHOP-09 (SHOULD).** Статистика магазина для админа: продажи за 7/30/90 дней, конверсия
карточка→заказ, среднее время ответа, доля споров, выручка в SOL и Stars, выгрузка CSV.

### 4.6 Цифровые товары и автовыдача

**FR-PROD-01 (MUST).** Типы цифровых товаров: `key` (лицензионный ключ/код), `file` (файл ≤ 100 МБ
в S3/MinIO, зашифрован), `account` (учётные данные), `subscription` (подписка/продление),
`service_code` (код услуги), `custom` (ручная выдача админом).

**FR-PROD-02 (MUST).** Карточка товара: название, описание (markdown, санитизация), категория,
цена в SOL и/или Stars, тип выдачи, остаток (для штучных — «осталось N»), срок действия/гарантия
(например «гарантия замены 30 дней»), скриншоты (≤ 5), рейтинг товара, кнопка «Купить» и
«Написать админу».

**FR-PROD-03 (MUST).** Сток для автовыдачи: единицы товара (`product_stock_items`) хранятся
**зашифрованными AES-256-GCM** (envelope, DEK товара); выдача — атомарно: `UPDATE … WHERE
status='free' LIMIT 1 RETURNING` + привязка к заказу; повторная выдача невозможна.
Порог остатка ⇒ уведомление админу магазина.

**FR-PROD-04 (MUST).** Для `file`: ссылка с одноразовым подписанным URL (TTL 15 мин, привязка к
заказу и user_id), лимит скачиваний (по умолчанию 5), журнал скачиваний.

**FR-PROD-05 (MUST).** Для `custom`: после оплаты заказ переходит в `processing`, админ магазина
выдаёт результат вручную в чате (вложение/текст — шифруются), затем переводит в `delivered`.
Таймер SLA (по умолчанию 24 ч) ⇒ автопредупреждение покупателю «Открыть спор» и штраф к
рейтингу магазина.

**FR-PROD-06 (MUST).** Модерация: новый товар попадает в очередь модерации (автоматические
проверки: запрещённые категории по юрисдикции покупателя/продавца, стоп-слова, дубли, цена
ниже себестоимости-порога) + ручная при первом товаре магазина и при жалобах. Статусы:
`draft → moderation → published → rejected → archived`.

**FR-PROD-07 (SHOULD).** Варианты/модификации товара (например «1 ключ / 5 ключей / 10 ключей»),
промокоды магазина, лимиты покупки на пользователя.

### 4.7 Механика заказа и статусы

**FR-ORD-01 (MUST).** Заказ создаётся из карточки товара (или корзиной из нескольких товаров одного
магазина — SHOULD). Состав: `order(items[], shop, buyer, amount, currency, delivery_type)`.

**FR-ORD-02 (MUST).** Статусы заказа (канонический набор, хранится в `orders.status` + полная
история в `order_status_history`):

| Статус | Код | Кто переводит | Таймер | Описание |
|---|---|---|---|---|
| Создан | `created` | система | 30 мин | ожидает оплаты, сток зарезервирован |
| Ожидает оплаты | `awaiting_payment` | система | 30 мин | выбран способ, ждём подтверждения |
| Оплачен (эскроу) | `paid_escrow` | платёжный модуль | — | средства заморожены на escrow-счёте |
| В работе | `processing` | админ магазина | SLA 24 ч | ручная выдача/подготовка |
| Выдан | `delivered` | автовыдача/админ | 72 ч на подтверждение | товар передан покупателю |
| Завершён | `completed` | покупатель/авто | — | средства раскрыты продавцу за вычетом комиссии |
| Спор открыт | `dispute_opened` | покупатель/админ магазина | 72 ч на ответ | эскроу заморожен, чат спора |
| На арбитраже | `in_arbitration` | арбитр | 7 сут | приглашён админ платформы |
| Возврат | `refunded` | арбитр/система | — | полный/частичный возврат покупателю |
| Отменён | `cancelled` | покупатель (до оплаты)/админ | — | сток освобождён |
| Истёк | `expired` | система | — | не оплачен в срок |

Допустимые переходы — конечный автомат (`docs/orders-disputes.md`, §3); любой недопустимый
переход ⇒ `409 INVALID_TRANSITION` + запись в аудит.

**FR-ORD-03 (MUST).** Оплата: внутренний SOL-баланс (мгновенно), Stars (мгновенно), внешний
депозит SOL (ожидание подтверждения сети). Комбинированная оплата (часть SOL + часть Stars) — SHOULD.

**FR-ORD-04 (MUST).** Эскроу: при `paid_escrow` средства списываются с баланса покупателя на
счёт `escrow:<order_id>` (двойная запись). При `completed` — перевод на `shop:<id>` минус комиссия
площадки (`platform:fees`). При `refunded` — возврат покупателю (полный/частичный по решению).

**FR-ORD-05 (MUST).** Автоподтверждение: через 72 ч после `delivered` без действий покупателя —
автоматический `completed` (уведомление за 24 ч). Покупатель может продлить окно на 72 ч один раз.

**FR-ORD-06 (MUST).** Отмена: до оплаты — свободно; после оплаты — только через спор или согласие
админа магазина (мгновенный возврат).

**FR-ORD-07 (MUST).** Экран заказа: номер, статус с прогресс-баром, товар, сумма и валюта,
таймер текущего этапа, кнопки действий по статусу («Оплатить», «Подтвердить получение»,
«Продлить», «Открыть спор», «Написать админу»), история статусов с метками времени,
квитанция/чек (PDF — SHOULD).

**FR-ORD-08 (MUST).** Уведомления о смене статуса: push в Telegram-бот + внутри TMA + email (опция).
Все уведомления — идемпотентны (dedup по `order_id+status`).

**FR-ORD-09 (SHOULD).** Корзина: несколько товаров одного магазина, единый эскроу, единый спор
по позициям (частичный возврат).

### 4.8 Мессенджер: чаты, группы, каналы, E2EE

**FR-MSG-01 (MUST).** Типы диалогов:
* `shop_support` — покупатель ↔ **админ магазина** (создаётся автоматически при первом обращении
  или при создании заказа; все обращения по магазину попадают сюда);
* `order` — чат конкретного заказа (покупатель, админ магазина, системные сообщения о статусах);
* `dispute` — чат спора (стороны + арбитр, с маскировкой, §4.9);
* `group` — группа магазина (админ + операторы + приглашённые покупатели, ≤ 200 участников);
* `channel` — канал (магазин или площадка публикует, подписчики читают, реакции/комментарии — SHOULD);
* `direct` — приватный чат двух пользователей (только по обоюдному согласию, E2EE обязателен).

**FR-MSG-02 (MUST).** Транспорт: **WebSocket Secure (WSS)**, единый сокет на клиента, бинарные
кадры с protobuf/JSON-payload, heartbeat ping/pong 25 с, авто-reconnect с экспоненциальной
задержкой (0.5…30 с) и догрузкой пропущенных сообщений по `last_seq`.

**FR-MSG-03 (MUST).** Хранение: **все тексты сообщений хранятся в БД в зашифрованном виде
(AES-256-GCM, envelope)**. В открытую часть записи попадают только метаданные: `chat_id, sender_id,
seq, ts, type, size, ciphertext_ref, e2ee_flag`. Поиск по содержимому приватных чатов не
предоставляется (осознанное ограничение E2EE); для `shop_support`/`order`/`dispute` возможен
серверный поиск по ciphertext после расшифровки на стороне сервера **только для арбитра и
модерации по процедуре** (§6.6) с записью в аудит.

**FR-MSG-04 (MUST).** **E2EE** для `direct` и по умолчанию для `dispute`:
* рукопожатие — X3DH-lite: у каждого устройства prekey-пакет (identity key Ed25519/X25519,
  signed prekey, one-time prekeys), публикация на сервере;
* сессионный ключ — X25519 ECDH → HKDF-SHA256 → root key;
* рэтчет — упрощённый Double Ratchet (симметричный рэтчет на направление + DH-рэтчет при смене
  устройства), каждый ключ одноразовый, после использования затирается;
* шифрование — AES-256-GCM, AAD = `chat_id||seq||sender_device_id`;
* сервер хранит только ciphertext, `sender_key_id`, `prekey_bundle` и метаданные.
Полная спецификация — `docs/security.md`, §5.

**FR-MSG-05 (MUST).** Серверное шифрование (ат-rest) применяется **всегда**, даже когда E2EE выключен
(групповые/служебные чаты): крипто-ядро (Rust) шифрует тело сообщения DEK'ом чата, DEK обёрнут KEK'ом
из KMS/HSM. Ключи никогда не покидают crypto-core в открытом виде; в БД — только wrapped-ключи.

**FR-MSG-06 (MUST).** Возможности сообщений: текст (≤ 4096 симв.), вложения (фото/видео/файл
до 25 МБ, шифруются на клиенте для E2EE-чатов), «товар» (карточка), «заказ» (карточка статуса),
«подарок», reply/цитата, редактирование (15 мин, с пометкой), удаление (у себя / у всех для
своих сообщений), прочитано/не прочитано, «печатает…», реакции (SHOULD).

**FR-MSG-07 (MUST).** Группы: создание админом магазина, роли (владелец/админ/оператор/участник),
invite-ссылки с TTL и лимитом, закреп сообщений, история для новых участников — по настройке.

**FR-MSG-08 (MUST).** Каналы: публикация магазином (анонсы, товары, акции) и площадкой
(новости, правила); подписка/отписка; счётчик просмотров; комментарии — SHOULD (отдельный чат).

**FR-MSG-09 (MUST).** Список чатов: сортировка по последнему сообщению, непрочитанные, закреплённые,
фильтр «Все / Магазины / Заказы / Споры / Каналы», поиск по названию (не по содержимому E2EE-чатов).

**FR-MSG-10 (MUST).** Анти-спам в мессенджере: лимит новых диалогов (5/час), лимит сообщений
(30/мин), фильтр ссылок/инвайтов для новых аккаунтов, жалобы («Пожаловаться» → очередь модератора),
мут и блок (блокировка не мешает системным чатам заказа/спора).

**FR-MSG-11 (SHOULD).** Оффлайн-доставка: очередь сообщений на устройство, TTL 30 сут,
«доставлено/прочитано»-статусы; push через Telegram-бот для закрытого приложения.

### 4.9 Споры, маскировка, арбитраж

**FR-DSP-01 (MUST).** Открыть спор могут: покупатель (после `paid_escrow`, до `completed`+7 сут),
админ магазина (при злоупотреблениях/чарджбэке), система (авто-спор при нарушении SLA выдачи).
Обязательные поля: причина (категория: «не выдано», «нерабочий товар», «не соответствует
описанию», «мошенничество», «иное»), описание (≥ 30 симв.), доказательства (вложения ≤ 10).

**FR-DSP-02 (MUST).** Чат спора `dispute:<order_id>` создаётся автоматически; в нём участвуют:
покупатель, админ магазина, (после эскалации) арбитр. Системные сообщения фиксируют каждый шаг
(открыт, ответ, эскалация, решение, исполнение).

**FR-DSP-03 (MUST).** **Маскировка (кто кого видит):**

| Наблюдатель | Видит вторую сторону как | Видит арбитра | Видит реальные ID |
|---|---|---|---|
| Покупатель | `Продавец #A17` (название магазина скрыто, если спор о мошенничестве; иначе — название магазина) | `Арбитр` | нет |
| Админ магазина | `Покупатель #K92` | `Арбитр` | нет |
| Арбитр | реальные ники/ID обеих сторон | — | **да** |
| Модератор (без назначения) | спор не виден | — | нет |

Правила маскировки:
* псевдонимы стабильны в рамках спора, генерируются детерминированно
  `HMAC(salt_dispute, user_id)` → алфавитно-цифровой код 3 знака, коллизии разрешаются суффиксом;
* метаданные (аватар, ник, история покупок, страна/город, IP, email) **не передаются** второй стороне;
* вложения проходят EXIF/метаданные-стриппинг и проверку на утечку идентификаторов;
* попытка раскрыть персональные данные в тексте ⇒ предупреждение и (при повторе) штраф к решению;
* арбитр назначается из пула, исключая конфликт интересов (аффилированность, предыдущие споры
  с той же стороной ≥ 3 за 90 дней); назначение — случайно с учётом нагрузки.

**FR-DSP-04 (MUST).** Эскалация и сроки: 72 ч на ответ стороны ⇒ автоэскалация; кнопка
**«Пригласить админа»** доступна обеим сторонам сразу после открытия; арбитр принимает спор
в работу ≤ 24 ч, решение ≤ 7 сут; продление — с уведомлением сторон и причиной.

**FR-DSP-05 (MUST).** Решения арбитра: `complete` (раскрыть эскроу продавцу), `refund_full`,
`refund_partial(amount)`, `replace` (продавец обязан выдать замену, SLA 48 ч), `dismiss`
(отклонить спор, эскроу раскрывается), `escalate_senior` (передать старшему арбитру),
`sanction` (применить санкцию к магазину/покупателю). Каждое решение содержит мотивировку
(≥ 100 симв.), ссылается на пункты правил и исполняется атомарно в ledger.

**FR-DSP-06 (MUST).** Апелляция: 72 ч после решения, рассматривает старший арбитр/супер-админ;
исполнение решения приостанавливается только для `refund_*` (средства остаются на эскроу до
решения апелляции).

**FR-DSP-07 (MUST).** Анти-фрод споров: счётчик «споры/заказы» у покупателя и у магазина;
порог 30 % за 90 дней ⇒ ручной скоринг, ограничение автовыдачи, повышенный депозит; повторные
необоснованные споры ⇒ `warn/restrict` (§FR-SHOP-08) или блокировка аккаунта покупателя.

**FR-DSP-08 (MUST).** Все действия в споре (открытие, каждое сообщение, эскалация, назначение,
решение, исполнение) логируются в `audit_log` (неизменяемая цепочка: `hash(prev)||hash(record)`),
хранение ≥ 5 лет.

### 4.10 Звёзды и цифровые подарки

**FR-STR-01 (MUST).** «Звёзды» = **Telegram Stars (XTR)** как основная внешняя единица +
внутренний учёт `stars_balance` в ledger. Пополнение: покупка Stars в Telegram (TMA
`openInvoice` / Bot API `sendInvoice` с `currency=XTR`), обмен SOL→Stars в обменнике (§4.11).

**FR-STR-02 (MUST).** За звёзды можно: покупать цифровые товары (если продавец включил приём Stars),
покупать **цифровые подарки**, оплачивать аренду магазина, бустить магазин, оплачивать комиссию
обменника. Курс SOL⇄Stars задаёт площадка (обновляется по оракулу цены SOL, спред ≤ 2 %).

**FR-STR-03 (MUST).** **Каталог подарков** (`gifts`): название, описание, редкость
(`common/rare/epic/legendary`), медиа (статика/анимация/стикер), цена в Stars и/или SOL,
лимит на пользователя, срок акции, признак «буст магазина» (даёт `gift_boost` в скоринге ленты),
признак «коллекционный» (NFT-like учёт внутри площадки, без выпуска в блокчейн на MVP).

**FR-STR-04 (MUST).** **Добавление подарков через админ-панель** — CRUD: создание, редактирование,
публикация/снятие, дублирование, загрузка медиа (≤ 20 МБ, WebM/MP4/PNG/WebP/Lottie JSON),
пакетный импорт CSV, предпросмотр карточки, история изменений, планировщик (start/stop по дате),
статистика продаж подарка.

**FR-STR-05 (MUST).** Покупка подарка: выбор способа (Stars / SOL) → подтверждение фактором 2 при
сумме ≥ порога (по умолчанию 1000 ⭐ / 5 SOL) → зачисление в инвентарь → «Подарить»
(пользователю или магазину) с сообщением (≤ 200 симв., шифруется). Получатель видит подарок в
профиле и в чате (карточка-подарок), отправитель — в истории. Подарок магазину увеличивает
`gift_boost` на 7 дней.

**FR-STR-06 (MUST).** Инвентарь подарков: витрина в профиле (сетка, редкость, дата), возможность
скрыть, передача другому пользователю запрещена после получения (анти-отмывочное правило),
кроме возврата площадки.

**FR-STR-07 (SHOULD).** Достижения/коллекции: наборы подарков, бейджи за активность, сезонные
события с ограниченными подарками.

### 4.11 Обмен (Exchange)

**FR-EXC-01 (MUST).** Экран «Обмен» (иконка в нижней панели) объединяет:
* **Кошелёк SOL**: баланс, депозитный адрес (персональный, base58 + QR), история транзакций,
  вывод (адрес, сумма, комиссия сети, подтверждение фактором 2, статусы `pending → broadcasting →
  confirmed / failed`);
* **Обменник**: SOL ⇄ Stars (и SOL ⇄ USDC — MAY) по курсу площадки с комиссией, предпросмотр
  «вы получите», допустимое отклонение курса (slippage) 0,5 %, лимиты (мин/макс, суточный),
  подтверждение фактором 2;
* **Платежи**: все входящие/исходящие операции с фильтрами и экспортом CSV;
* **Лимиты и безопасность**: суточный лимит вывода по умолчанию 50 SOL (повышение — через
  поддержку + фактор 2 + задержка 24 ч на смену адреса вывода — «withdrawal whitelist cooling»).

**FR-EXC-02 (MUST).** Депозит SOL (кастодиальная модель, подробно — `docs/solana.md`):
персональный депозитный адрес на пользователя (HD-деривация ed25519 от мастер-ключа), сканер
блокчейна (RPC + WebSocket-подписка на слоты/сигнатуры), зачисление после **32 подтверждений**
(≈ 15 с × 32) для сумм < 100 SOL и **64** для больших; учёт `memo`/amount-unique для сопоставления;
минимальная сумма зачисления 0.01 SOL; внутренние переводы между пользователями — мгновенные
записи ledger (без блокчейна).

**FR-EXC-03 (MUST).** Вывод: только на верифицированные адреса (whitelist), задержка первого вывода
на новый адрес 24 ч, лимиты, обязательный фактор 2, ручная аппрув-очередь для сумм ≥ 100 SOL
(двойной контроль: инициатор + супер-админ, 4-глаза), подпись транзакции — **только в Rust
crypto-core** (закрытый ключ никогда не покидает crypto-core; в проде — HSM).

**FR-EXC-04 (MUST).** Все операции ledger — двойная запись, идемпотентность по `idempotency_key`,
ежесуточная сверка (`sum(debits) == sum(credits)`), расхождение ⇒ алерт P1 и блокировка вывода.

**FR-EXC-05 (SHOULD).** Внутренние P2P-переводы между пользователями (по нику), с подтверждением
получателя и анти-фрод-лимитом для новых аккаунтов.

### 4.12 Отзывы и рейтинг

**FR-REV-01 (MUST).** Отзыв оставляется после `completed` (окно 30 сут), строго **1 отзыв на заказ**
(привязка `reviews.order_id UNIQUE`), только верифицированная покупка ⇒ бейдж «Подтверждённая
покупка». Состав: оценка 1–5, текст (≤ 1000), фото (≤ 3), оценки по критериям (скорость выдачи,
соответствие описанию, общение с админом) — SHOULD.

**FR-REV-02 (MUST).** Рейтинг магазина = байесовское среднее:
`bayes = (C*m + Σratings) / (C + n)`, где `C = 10` (априорное число отзывов), `m = 3.8` (среднее по
площадке). Отображается с точностью 0.1. Рейтинг товара считается отдельно.

**FR-REV-03 (MUST).** Ответ продавца (1 ответ на отзыв, ≤ 500 симв.), редактирование отзыва
покупателем в течение 7 сут (с пометкой «изменён»), удаление — только модерацией.

**FR-REV-04 (MUST).** Анти-фрод отзывов: запрет накрутки (совпадение device-fingerprint/IP-подсетей,
массовые отзывы новых аккаунтов, отзывы до фактической выдачи), автомодерация (стоп-слова, ссылки,
оскорбления, персональные данные — маскируются), ручная модерация по жалобе (SLA 24 ч),
санкции за накрутку (§FR-SHOP-08) и обнуление рейтинга при доказанной накрутке.

**FR-REV-05 (MUST).** Жалоба на отзыв: причина (спам, оскорбления, раскрытие ПД, недостоверность),
очередь модератора, статусы `pending/approved/rejected`, уведомление автора.

**FR-REV-06 (SHOULD).** Агрегаты на карточке магазина: распределение оценок 1–5, «98 % положительных»,
среднее время ответа админа, доля заказов со спорами.

### 4.13 Профиль

**FR-PRF-01 (MUST).** Экран «Профиль» (иконка нижней панели): аватар, ник, email/Telegram,
страна и город (редактируется с ограничениями FR-GEO-04), балансы (SOL / Stars), инвентарь
подарков, мои магазины (если есть) со статусом аренды, мои заказы, мои отзывы, настройки.

**FR-PRF-02 (MUST).** Настройки: безопасность (смена пароля, оба 2FA-фактора, backup-коды,
активные сессии, withdrawal-whitelist, журнал входов), приватность (кто может писать, видимость
гео, персонализация ленты), уведомления (push/email/бот по типам событий), язык, тема,
валюта отображения, удаление аккаунта (soft-delete 30 сут с восстановлением, затем анонимизация).

**FR-PRF-03 (MUST).** Публичный профиль: ник, аватар, страна (без города по умолчанию),
подарки-витрина, отзывы о пользователе как о продавце (если есть магазины), дата регистрации
(«на площадке с …»), бейджи (verified, crown, top-seller).

### 4.14 Админ-панель

**FR-ADM-01 (MUST).** Отдельный раздел (доступ только привилегированным ролям, вход — фактор 1 +
фактор 2 + проверка IP-allowlist в проде, отдельный поддомен `admin.`). Разделы:

| Раздел | Возможности |
|---|---|
| Дашборд | GMV (SOL/Stars), комиссии, новые пользователи/магазины, активные аренды, споры в очереди, инциденты безопасности, health сервисов |
| Пользователи | поиск, карточка, блокировки/разблокировки, сброс 2FA (по заявке), роли, история входов, привязанные кошельки |
| Магазины | список/фильтры, карточка, санкции, передача владения, ручное продление аренды, verified/crown-флаги |
| Аренда и тарифы | CRUD тарифов (цена, лимиты, комиссия, boost), промокоды, отчёты по продлениям и churn |
| Товары и модерация | очередь модерации, стоп-слова, запрещённые категории, гео-блокировки, takedown по жалобе |
| **Подарки** | **CRUD подарков** (§FR-STR-04), медиа-библиотека, импорт CSV, планировщик, статистика |
| Заказы | поиск по всем полям, ручная смена статуса (с причиной и фактором 2), ре-выдача товара, отмена, рефанд |
| Споры | очередь, назначение арбитров, карточка спора (реальные ID), решения, апелляции, статистика и SLA |
| Финансы | ledger-отчёты, сверка эскроу, депозиты/выводы SOL, комиссия площадки, выгрузки CSV, reconciliation-отчёт |
| Кошельки | горячий/холодный баланс, sweep-операции (4-глаза), лимиты, blacklist адресов, мониторинг сканера |
| Отзывы | очередь жалоб, скрытие/удаление, санкции за накрутку |
| Безопасность | auth_events, rate-limit-метрики, заблокированные IP, активные атаки, управление WAF-правилами, аудит-лог (неизменяемый) |
| Контент | страны/города, категории, шаблоны уведомлений, тексты правил, баннеры в каналах |
| Настройки | пороги 2FA, лимиты, комиссии, курс SOL⇄Stars, фиче-флаги |

**FR-ADM-02 (MUST).** Каждое действие админа — в `audit_log` с `actor, action, target, before/after
(diff), reason, ip, user_agent, totp_step2_verified`. Деструктивные действия (бан, рефанд, смена
статуса, sweep, сброс 2FA) требуют **фактор 2** и (для финансов ≥ порога) **второго админа (4-глаза)**.

**FR-ADM-03 (MUST).** Ролевая модель RBAC + ABAC-ограничения (например, арбитр видит только
назначенные споры; модератор — только очереди). Разделение окружений: `admin` в проде недоступен
извне без VPN/allowlist.

### 4.15 Нижняя панель навигации

**FR-NAV-01 (MUST).** Нижняя панель в стиле Telegram, **4 иконки**:
1. **Магазины** — лента и поиск (§4.4);
2. **Чаты** — список диалогов, группы, каналы, споры (§4.8, §4.9), бейдж непрочитанных;
3. **Обмен** — кошелёк SOL, обменник, платежи (§4.11);
4. **Профиль** — профиль, настройки, заказы, подарки (§4.13).

**FR-NAV-02 (MUST).** Поведение: фиксирована внизу (safe-area insets), активная иконка подсвечена
акцентным цветом, бейджи непрочитанного (число/точка), свайп между разделами — MAY,
сохранение состояния скролла при возврате, учёт `theme_params` Telegram (светлая/тёмная).

**FR-NAV-03 (MUST).** Доступность: размер тач-цели ≥ 44×44 px, aria-подписи, контраст ≥ 4.5:1,
поддержка системного шрифта Telegram, работа при `prefers-reduced-motion`.

## 6. Криптография и защита данных

> Полная спецификация: **`docs/security.md`**. Здесь — обязательный минимум.

**FR-SEC-01 (MUST).** Транспорт: TLS 1.3 (минимум 1.2 с forward-secrecy-сайферами), HSTS
(max-age ≥ 1 год, preload), WSS для мессенджера, никакого plaintext-трафика, OCSP-stapling.

**FR-SEC-02 (MUST).** Шифрование в БД: **AES-256-GCM** envelope-схема. Для каждого домена данных
(сообщения чата, сток товаров, персональные данные, приватные ключи) — отдельный **DEK**; DEK
обёрнут **KEK** из KMS/HSM (HashiCorp Vault Transit / AWS KMS / cloud HSM). Ротация KEK — 90 дней,
ротация DEK — 365 дней с re-encrypt фоном. В БД хранится только `ciphertext || nonce || tag` и
идентификатор версии ключа (`key_id`).

**FR-SEC-03 (MUST).** Все текстовые сообщения передаются по **WSS** и хранятся в БД **только в
зашифрованном виде** (AES-256). Приватные чаты — дополнительно **E2EE** (FR-MSG-04).

**FR-SEC-04 (MUST).** Пароли — Argon2id (§FR-AUTH-03); секреты 2FA — в БД в зашифрованном виде
(DEK `auth`); backup-коды — HMAC-SHA256 с солью; приватные ключи Solana — только в crypto-core
(Rust), в проде — HSM, никогда в логах и БД в открытом виде.

**FR-SEC-05 (MUST).** Управление ключами: мастер-ключ (корень доверия) — оффлайн/HSM, доступ 4-глаза;
иерархия `master → KEK(domain) → DEK(object)`; процедура ceremony для генерации и ротации;
аварийное восстановление (shamir-разделение мастер-ключа 3-из-5 — MAY).

**FR-SEC-06 (MUST).** Контроль доступа к расшифровке: любой вызов `decrypt` в crypto-core требует
service-token + аудит; расшифровка служебных чатов модерацией — только по ticket-процедуре с
одобрением и записью в неизменяемый аудит (§6.6 в `docs/security.md`).

**FR-SEC-07 (MUST).** Защита приложения: CSP (strict-dynamic + nonce), X-Frame-Options/`frame-ancestors`
(для TMA — разрешённые origins Telegram), `X-Content-Type-Options`, `Referrer-Policy`,
`Permissions-Policy`, санитизация HTML (DOMPurify-эквивалент), CSRF-токены для cookie-режима,
валидация `telegram init_data` HMAC, отсутствие секретов в клиентском коде.

**FR-SEC-08 (MUST).** Секреты и данные карт/ключей не попадают в логи; логирование — с маскированием
(`email → e***@d**, address → 0x12…ab, ciphertext → <enc:128b>`); PII в метриках запрещено.

**FR-SEC-09 (MUST).** Целостность: аудит-лог — хэш-цепочка; артефакты сборки — подписаны (cosign);
SBOM (CycloneDX) для каждого релиза; зависимости — сканирование (govulncheck, cargo-audit) в CI.

**FR-SEC-10 (MUST).** Резервные копии шифруются (age/AES-256-GCM) отдельным ключом, хранятся в
другом регионе, восстановление проверяется ежеквартально.

## 7. Защита от брутфорса и DDoS

> Полная спецификация и правила: **`docs/security.md`**, §7–§9.

**FR-ABF-01 (MUST).** Анти-брутфорс на входе: экспоненциальная задержка и лок (5 неверных паролей
⇒ 15 мин, 15 ⇒ 24 ч + поддержка), учёт связки `email+IP`, `IP`, `device_fingerprint`, `ASN`;
капча (Turnstile/hCaptcha) после 3 неудач; глобальный «шторм-режим» при аномалии (все входы с
капчей).

**FR-ABF-02 (MUST).** Анти-credential-stuffing: проверка пароля по breach-корпусу (k-anonymity
API — SHOULD, локальный bloom — MUST), блокировка однотипных попыток по всему IP-диапазону,
обязательная капча для входов из «рисковых» ASN/VPN/Tor (Tor — запрет для привилегированных ролей).

**FR-ABF-03 (MUST).** Rate-limit на **все** эндпоинты (token bucket в Rust-движке, распределённый
счётчик в Redis): профили `public 60/min`, `auth 10/min`, `2fa 1/min`, `ws-connect 5/min`,
`ws-msg 60/min`, `payment 10/min`, `admin 120/min`. Ответ `429` с `Retry-After` и заголовком
`X-RateLimit-*`.

**FR-ABF-04 (MUST).** Анти-DDoS L3/L4: провайдер с Anycast-скраббингом (Cloudflare Magic Transit /
AWS Shield Advanced), SYN-cookies, ограничение UDP, geo-IP блок для нецелевых стран (настраивается),
Blackhole-процедура для подсетей атакующих.

**FR-ABF-05 (MUST).** Анти-DDoS L7: WAF (OWASP CRS + кастомные правила), JS/TLS-challenge для
аномального трафика, rate-limit по IP+cookie+JA3/JA4-фингерпринту, «под пчелой» (bot fight mode),
приоритизация: API-эндпоинты оплаты и WS — повышенные лимиты для авторизованных, жёсткие для
анонимных; статический контент — через CDN с кэшем; graceful shutdown и очереди при перегрузке
(backpressure, `503 + Retry-After` при превышении бюджета нагрузки).

**FR-ABF-06 (MUST).** Защита WS: лимит соединений на IP/пользователя (по умолчанию 5/10), лимит
сообщений/минуту, максимальный размер кадра 64 КБ, обязательная аутентификация в первые 10 с
после подключения (иначе разрыв), медленный «read timeout», защита от slowloris,
дедупликация по `client_msg_id`.

**FR-ABF-07 (MUST).** Защита от регистрации ботами: капча + подтверждение Telegram/email +
лимит регистраций с IP/ASN/устройства (3/сутки) + отложенная активация финансовых функций для
новых аккаунтов («прогрев»: 24 ч без вывода средств и без создания магазина).

**FR-ABF-08 (MUST).** Мониторинг атак: метрики (429/с, 401/с, WS-подключения, challenge-pass rate),
дашборд «Атака», автоматические реакции (ban IP на N мин при пороге), алерт P1 в Telegram-канал
безопасности, еженедельный отчёт.

**FR-ABF-09 (SHOULD).** Device-fingerprint (без PII): hash(TLS-JA4 + UA + экран + часовой пояс +
canvas-сигнатура — с согласия), «доверенные устройства» (не требуем фактор 1 повторно 30 дней).

## 8. Архитектура и стек

> Детали, схемы и контракты: **`docs/architecture.md`**, **`docs/api.md`**, **`docs/data-model.md`**.

**FR-ARC-01 (MUST).** Стиль: модульный монолит на Go с выделенными «горячими» сервисами на Rust
(разделение по безопасности и нагрузке), готовый к распаду на микросервисы (чёткие границы модулей,
событийная шина).

**FR-ARC-02 (MUST).** Компоненты:

| Компонент | Язык | Ответственность |
|---|---|---|
| `siteed-api` | **Go** | REST API, аутентификация/сессии, бизнес-логика магазинов/заказов/споров/отзывов/подарков/аренды, админка |
| `siteed-ws` | **Go** | WebSocket-хаб, доставка сообщений, presence, typing, догрузка по `last_seq` |
| `crypto-core` | **Rust** | AES-256-GCM envelope (encrypt/decrypt), HKDF/PBKDF2/HMAC, TOTP-verify, Ed25519-ключи и подпись Solana-транзакций, base58, rate-limit и анти-фрод-движок |
| `sol-scanner` | **Go** (+Rust для подписи) | Мониторинг депозитов, построение/подпись/отправка транзакций, sweep, reconciliation |
| `worker` | **Go** | Асинхронные задачи: уведомления, таймеры заказов/аренды, авто-споры, модерация, отчёты |
| `frontend-tma` | HTML/CSS/JS | Telegram Mini App |
| `admin-web` | тот же SPA (роут `/admin`) | Админ-панель |
| Хранилища | — | PostgreSQL 16 (осн. данные, FTS), Redis 7 (кэш, rate-limit, pub/sub, очереди), S3/MinIO (медиа, файлы товаров), Vault/KMS (KEK) |

**FR-ARC-03 (MUST).** Взаимодействие Go ↔ Rust crypto-core: внутренний HTTP/1.1 (или UNIX-сокет)
по приватной сети/mTLS, JSON-контракт (`/v1/encrypt`, `/v1/decrypt`, `/v1/totp/verify`,
`/v1/solana/sign`, `/v1/ratelimit/check`, `/v1/fraud/score`), таймаут 200 мс, circuit-breaker,
**Go-fallback** на `crypto/*` при недоступности (тот же формат ciphertext) + алерт P2.

**FR-ARC-04 (MUST).** Событийная шина: `events` (outbox-паттерн в PostgreSQL → Redis Streams/NATS),
потребители: worker, sol-scanner, аналитика, уведомления. Гарантия at-least-once + идемпотентность
потребителей.

**FR-ARC-05 (MUST).** Конфигурация: 12-factor, всё через env/секреты; фиче-флаги; отдельные
конфиги `dev/stage/prod`; никаких секретов в репозитории (pre-commit + gitleaks в CI).

## 11. Риски и допущения

| ID | Риск | Вероятность | Влияние | Меры |
|---|---|---|---|---|
| R1 | Юридический статус кастодиальной площадки и цифровых товаров в юрисдикциях запуска | средняя | критическое | Юр-экспертиза до этапа 4, гео-блокировки категорий, лимиты, возможность отключения кастодии в пользу некастодиального эскроу (`docs/solana.md`, §9) |

| R4 | Волна мошеннических магазинов | высокая | высокое | Модерация первых товаров, депозит/аренда как фильтр, рейтинг и споры, санкции, автоматический скоринг |
| R5 | DDoS во время запуска/акции | высокая | среднее | Cloudflare + scrubbing, rate-limit, статический кэш, план blackhole, учения |
| R6 | Падение Solana RPC / форк сети | средняя | среднее | Несколько RPC-провайдеров, подтверждение по 32/64 слотам, ручная очередь при рассинхроне, идемпотентность зачислений |
| R7 | Потеря E2EE-ключей пользователем | высокая | среднее | Backup-коды, мульти-устройство, понятный UX-дисклеймер, восстановление истории недоступно (осознанно) |
| R8 | Невыполнение обязательств по эскроу при кассовом разрыве | низкая | критическое | Раздельный учёт escrow-счетов, ежедневная сверка, резерв ликвидности, запрет использования эскроу-средств |
| R9 | Накрутка отзывов и рейтинга | высокая | среднее | Верификация покупки, анти-фрод-скоринг, байесовский рейтинг, санкции и обнуление |
| R10 | Зависимость от Telegram Stars API (изменения/лимиты) | средняя | среднее | Абстракция платёжного провайдера, внутренний курс, возможность оплаты только в SOL |

юрлицо и банковский/крипто-партнёр для off-ramp (не входит в ТЗ); A3 — целевые рынки на старте:
RU-язычная аудитория + ЕС/СНГ, с гео-блоком санкционных категорий; A4 — нагрузка MVP ≤ 5 000 DAU;
A5 — дизайн-макеты предоставляются заказчиком или разрабатываются в стиле Telegram (этап 0).
