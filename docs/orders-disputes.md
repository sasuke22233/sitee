## 1. Жизненный цикл заказа

### 1.1 Статусы
| Статус | Код | Входит по | Таймер | Что доступно покупателю | Что доступно админу магазина |
|---|---|---|---|---|---|
| Создан | `created` | оформление | 30 мин до `expired` | «Оплатить», «Отменить», «Написать админу» | «Отменить» |
| Ожидает оплаты | `awaiting_payment` | выбран способ (внешний депозит) | 30 мин | «Оплатить», «Отменить» | — |
| Оплачен (эскроу) | `paid_escrow` | подтверждение оплаты | — | «Открыть спор» | «Взять в работу», «Выдать», «Отменить с возвратом» |
| В работе | `processing` | действие админа | SLA (по товару, по умолчанию 24 ч) | «Открыть спор», «Написать админу» | «Выдать» |
| Выдан | `delivered` | автовыдача / ручная выдача | 72 ч до автоподтверждения | «Подтвердить», «Продлить (1 раз)», «Открыть спор» | — |
| Завершён | `completed` | подтверждение / таймер | 30 сут окно отзыва | «Оставить отзыв» | «Ответить на отзыв» |
| Спор открыт | `dispute_opened` | открытие спора | 72 ч на ответ | «Ответить», «Пригласить админа», «Приложить» | «Ответить», «Приложить», «Предложить возврат» |
| На арбитраже | `in_arbitration` | эскалация / авто | 7 сут на решение | «Ответить арбитру» | «Ответить арбитру» |
| Возврат | `refunded` | решение | — | «Открыть новый спор (1 раз)» | — |
| Отменён | `cancelled` | отмена до/после оплаты | — | — | — |
| Истёк | `expired` | таймаут оплаты | — | «Оформить заново» | — |

### 1.2 Конечный автомат (допустимые переходы)
```
created          → awaiting_payment | paid_escrow | cancelled | expired
awaiting_payment → paid_escrow | cancelled | expired
paid_escrow      → processing | delivered | dispute_opened | cancelled(с возвратом)
processing       → delivered | dispute_opened
delivered        → completed | dispute_opened
dispute_opened   → in_arbitration | completed | refunded
in_arbitration   → completed | refunded
completed        → dispute_opened (в окне 7 сут) → in_arbitration → refunded|completed
refunded         → dispute_opened (1 раз, апелляция)
cancelled|expired→ (терминальные)
```
Любой другой переход ⇒ `409 INVALID_TRANSITION` + запись в аудит. Все переходы пишутся в
`order_status_history` с `actor_kind` (system/buyer/shop/arbiter/admin/timer).

### 1.3 Таймеры (worker, идемпотентные джобы)
| Таймер | Условие | Действие |
|---|---|---|
| `pay_timeout` | `created/awaiting_payment` > 30 мин | → `expired`, снятие резерва стока |
| `delivery_sla` | `processing` > SLA товара | уведомление покупателю + «Открыть спор», штраф к `response_p50` |
| `auto_confirm` | `delivered` > 72 ч | → `completed`, раскрытие эскроу, уведомление за 24 ч |
| `dispute_reply` | `dispute_opened` > 72 ч без ответа | автоэскалация → `in_arbitration` |
| `arbitration_sla` | `in_arbitration` > 7 сут | алерт старшему арбитру, авто-продление с уведомлением |
| `review_window` | `completed` > 30 сут | окно отзыва закрывается |
| `rent_renew` | T−24 ч | списание автопродления |
| `rent_grace` | T+72 ч | `suspended` магазина |

### 1.4 Автовыдача (атомарный алгоритм)
```sql
BEGIN;
  -- 1) резерв/списание стока
  UPDATE product_stock_items SET status='sold', sold_at=now()
   WHERE id = (SELECT id FROM product_stock_items
                WHERE product_id=$1 AND status='reserved' AND reserved_by=$2
                ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED)
   RETURNING id, payload_ct;
  -- 2) запись выданного контента в order_items.delivered_payload_ct
  -- 3) переход статуса delivered + история + событие
  -- 4) ledger: user → escrow (если ещё не проведён)
COMMIT;
```
При `stock_free = 0` заказ не создаётся (`422 STOCK_EMPTY`); резерв снимается по `pay_timeout`.

## 2. Эскроу и раскрытие средств

```
оплата:        user:X:SOL  → escrow:ORD           (полная сумма)
завершение:    escrow:ORD  → shop:S:SOL (сумма − комиссия)
                           → platform:fees (комиссия по тарифу)
возврат полн.: escrow:ORD  → user:X:SOL
возврат част.: escrow:ORD  → user:X:SOL (amount) + shop:S:SOL/platform:fees (остаток)
```
Раскрытие происходит **только** при `completed` (подтверждение покупателя, автоподтверждение
или решение арбитра `complete`). Пока открыт спор — средства на `escrow:ORD` недоступны никому.

## 3. Споры

### 3.1 Причины и требования к открытию
| `reason_code` | Описание | Обязательные доказательства |
|---|---|---|
| `not_delivered` | товар не выдан | скриншот чата/статуса |
| `broken` | нерабочий товар | скрин/видео ошибки, лог |
| `not_as_described` | не соответствует описанию | сравнение с карточкой |
| `fraud` | признаки мошенничества | любые материалы |
| `sla_violation` | нарушен срок выдачи | метки времени |
| `other` | иное | описание ≥ 100 симв. |

Валидация: заказ в допустимом статусе (§1.2), описание ≥ 30 символов, ≤ 10 вложений
(≤ 25 МБ каждое, стриппинг метаданных), не более 1 активного спора на заказ,
фактор `ops` подтверждён.

### 3.2 Маскировка (кто кого видит)
| Данные | Покупатель | Админ магазина | Арбитр |
|---|---|---|---|
| Псевдоним стороны | `Продавец #A17` | `Покупатель #K92` | реальные ники |
| Реальный `user_id`/ник | ❌ | ❌ | ✅ |
| Аватар | ❌ (дефолтная иконка роли) | ❌ | ✅ |
| Страна/город | ❌ | агрегат «страна + TZ» по заказу | ✅ |
| История покупок/продаж | ❌ | ❌ | ✅ (сводка) |
| Email/Telegram/IP | ❌ | ❌ | ✅ только при необходимости (аудит-запись `dispute.reveal`) |
| Содержание других споров стороны | ❌ | ❌ | ✅ (сводка статистики) |

Генерация псевдонима: `code = base36(HMAC-SHA256(salt_dispute, user_id))[0:3].toUpperCase()`,
при коллизии в рамках спора — суффикс `-2`. Соль спора уникальна и не переиспользуется.
Псевдонимы стабильны в рамках одного спора (включая апелляцию) и различаются между спорами
(нельзя скоррелировать стороны между спорами).

Дополнительно: **фильтр раскрытия ПД в тексте** — при отправке сообщения в чат спора сервер
маскирует паттерны (email, телефон, @username, адреса кошельков, IP) для не-арбитра и
предупреждает отправителя; повторные попытки ⇒ `warn` и учёт при решении.

### 3.3 Процесс
```
1. Открытие          → dispute_opened, чат dispute:<order>, псевдонимы, таймер 72 ч
2. Ответ стороны     → сообщения в чат (шифруются доменом dispute), вложения
3. «Пригласить админа»→ in_arbitration, автоназначение арбитра из пула (случайно, с учётом
                        нагрузки и исключения конфликта интересов), уведомление
4. Рассмотрение      → арбитр видит реальные ID, историю заказа, переписку (по процедуре §4.6
                        docs/security.md), доказательства, статистику стороны
5. Решение           → resolution + мотивировка (≥100 симв.) + фактор ops
6. Исполнение        → атомарно: ledger-проводки + смена статуса заказа + санкции (если есть)
7. Апелляция (72 ч)  → старший арбитр; для refund_* исполнение приостанавливается
```

### 3.4 Решения и их исполнение
| `resolution` | Ledger | Статус заказа | Дополнительно |
|---|---|---|---|
| `complete` | escrow → shop + fees | `completed` | окно отзыва открывается |
| `refund_full` | escrow → user | `refunded` | сток помечается `void` или возвращается (по типу товара) |
| `refund_partial(amount)` | escrow → user (amount) + shop/fees (остаток) | `refunded` | фиксация доли |
| `replace` | без движения средств | `processing` | SLA 48 ч на замену, иначе авто-`refund_full` |
| `dismiss` | escrow → shop + fees | `completed` | `dispute_loss_penalty` покупателю |
| `escalate_senior` | — | `in_arbitration` | переназначение |
| `sanction` | — | по контексту | `warn/restrict/suspend/ban` магазину или покупателю |

### 3.5 Назначение арбитра (антиконфликт)
Исключаются кандидаты: с ролью ниже `arbiter`; аффилированные (тот же device-fingerprint/IP-подсеть/
реферальная связь с любой из сторон); имеющие ≥ 3 споров с той же стороной за 90 дней;
загруженные сверх лимита (по умолчанию 10 активных). Выбор — взвешенно-случайный
(вес = 1/(1+active)), с ротацией и учётом часового пояса (SLA 24 ч на принятие).

### 3.5.1 Апелляция (FR-DSP-06)
| Параметр | Значение |
|---|---|
| Окно подачи | 72 часа с момента resolved/dismissed |
| Кто подаёт | сторона спора: покупатель или продавец |
| Сколько раз | одна апелляция на спор (appeal_of ссылается на решённый спор) |
| Обоснование | не менее 30 символов, попадает в таймлайн как appeal |
| Статус спора | appeal |
| Исполнение | refund_* и partial приостанавливаются — средства остаются на эскроу (execution_suspended: true) |
| Арбитр | старший: роль arbiter/superadmin, не сторона спора и не арбитр первого решения; выбор — наименее загруженный |

Ошибки: ALREADY_APPEALED (409), DISPUTE_NOT_APPEALABLE (409), APPEAL_WINDOW_CLOSED (409),
FORBIDDEN (403). Решение старшего арбитра — финальное: повторная апелляция и эскалация
недоступны, execution_suspended снимается, исполнение выполняется по новому решению.
POST /api/v1/disputes/{id}/appeal — в docs/api.md §5.

### 3.6 Метрики споров
`disputes_opened_total{reason}`, `dispute_resolution_time_seconds`,
`disputes_by_resolution{resolution}`, `shop_dispute_rate`, `buyer_dispute_rate`,
`appeal_rate`, `sla_breach_total`. Порог `shop_dispute_rate > 15 %` за 90 дней ⇒ автоматическая
проверка и, при подтверждении, санкция.

## 4. Мессенджер в контексте заказа

* При создании заказа автоматически открывается/используется чат `order:<id>` (участники:
  покупатель + админ магазина) и/или `shop_support` — по настройке магазина;
* системные сообщения (тип `system`) фиксируют статусы: «Оплата получена, средства в эскроу»,
  «Товар выдан», «Открыт спор», «Арбитр назначен», «Решение: возврат 1.2 SOL»;
* карточки (`order_card`, `product_card`, `gift_card`) рендерятся клиентом по данным сервера;
* все сообщения чатов заказа/спора шифруются at-rest (домен `msg`/`dispute`); E2EE — для
  `direct` и по выбору для `dispute` (с дисклеймером об ограничениях арбитража);
* админ магазина обязан ответить в пределах SLA тарифа; иначе — автопредупреждение и штраф
  к `response_p50_s`, при повторе — снижение позиции в ленте.

## 5. UX-требования к экранам заказа и спора

1. Прогресс-бар статусов с метками времени и таймером текущего этапа («Подтвердите до …»,
   «Ответ продавца ожидается до …»).
2. Явные действия по статусу (серверный `actions[]`), без «мёртвых» кнопок.
3. В споре — плашка маскировки: «Вы видите продавца как **Продавец #A17**. Личные данные скрыты.
   Арбитр увидит обе стороны.»
4. Кнопка **«Пригласить админа»** — заметная, с объяснением последствий и сроков.
5. Все суммы — с указанием актива и комиссии; подтверждение — модалкой с фактором `ops`.
6. История статусов и переписка доступны офлайн (кэш клиента) для чтения.
