# Приложение E. Solana: кастодиальная модель, депозиты, выводы, сверка

Ссылки: `TZ.md` FR-EXC-01…05, FR-SEC-04, FR-ARC-02. Модель выбрана заказчиком:
**кастодиальный внутренний баланс** (площадка хранит ключи, пользователи видят балансы).

---

## 1. Почему кастодиальная модель (и её границы)

| Плюс | Минус / риск | Компенсация |
|---|---|---|
| Мгновенные внутренние переводы и эскроу без комиссии сети | Площадка — кастодиан (юридический риск R1) | Юр-экспертиза, раздельный учёт escrow, запрет использования средств клиентов |
| Простой UX: баланс, оплата в 1 клик | Компрометация hot-кошелька = потеря средств | Лимит hot-баланса, авто-sweep в cold, HSM, 4-глаза |
| Одна транзакция на вывод пачкой (batch) | Зависимость от доступности RPC | 2+ RPC-провайдера, очередь, ручной режим |
| Возможность платить комиссию площадки централизованно | Регуляторные требования к отчётности | Ledger двойной записи, daily reconciliation, выгрузки |

**Важно:** средства пользователей и эскроу учитываются на отдельных ledger-счетах и **не**
используются площадкой для собственных операций. Инвариант (§6) проверяется непрерывно.

## 2. Архитектура кошелькового контура

```
                        ┌─────────────────────┐
  пользователь ────────▶│  siteed (Go)        │  баланс, лимиты, whitelist, 2FA
                        │  wallet + ledger    │
                        └──────┬──────────────┘
                               │ 1) адрес депозита (публичная часть)
                               │ 2) запрос подписи (tx_bytes, purpose)
                        ┌──────▼──────────────┐          ┌──────────────┐
                        │  crypto-core (Rust) │◀────────▶│ Vault / HSM  │  MK_sol, KEK[wallet]
                        │  HD-деривация ed25519│          └──────────────┘
                        │  Ed25519-подпись    │
                        └──────┬──────────────┘
                               │ подписанная транзакция
                        ┌──────▼──────────────┐      ┌───────────────────────┐
                        │  sol-scanner (Go)   │◀────▶│ Solana RPC ×2 + WSS    │
                        │  депозиты/выводы    │      │ getSignatureStatuses,  │
                        │  sweep, reconcil.   │      │ sendTransaction, slots │
                        └─────────────────────┘      └───────────────────────┘
```

* Приватные ключи **никогда** не покидают crypto-core: Go оперирует `account_id` и `address`.
* Каждый запрос подписи содержит `purpose`, `amount`, `dest`, `idempotency_key`, `actor` и
  проверяется на лимиты и whitelist **внутри Rust** (двойной контроль, а не только в Go).

## 3. Депозитные адреса (HD-деривация)

* Стандарт: **SLIP-0010 ed25519**, путь `m/44'/501'/<account_index>'/0'` (501 = coin type Solana).
* Индекс `account_index` = стабильный номер пользователя (`users.seq`), чтобы адрес был
  детерминирован и восстанавливаем из MK без БД.
* На MVP допускается **один адрес на пользователя**; для точной атрибуции без `memo` используется
  метод «уникальная сумма» (`expected_amount` с точностью до 9 знаков, например `1.234567891 SOL`)
  и/или `memo`-инструкция в транзакции отправителя.
* Адрес показывается в UI как base58 + QR; смена адреса — только через поддержку (старый остаётся
  активным для приёма 90 дней).

**Проверка адреса на вводе (вывод):** base58-алфавит, длина 32 байта, не совпадает с депозитными
адресами площадки и со known-scam-списком, не PDA/program-owned (проверка `getAccountInfo`).

## 4. Приём депозитов

1. `sol-scanner` подписан на слоты (`logsSubscribe` по адресам + `blockSubscribe` как fallback)
   и параллельно опрашивает `getSignaturesForAddress` по каждому активному адресу (пачками,
   rate-limit RPC).
2. Найденная транзакция → `sol_transactions(status='seen')` с `signature` (unique ⇒ идемпотентность).
3. Подтверждения: `getSignatureStatuses(searchTransactionHistory=true)`; зачисление после
   **32 подтверждений** (сумма < 100 SOL) или **64** (≥ 100 SOL).
4. Зачисление: атомарная ledger-операция `deposit` (`credit user`, `debit platform:custody`),
   статус `credited`, событие `wallet.deposit.credited` → уведомление пользователя.
5. Неизвестный адрес / неполная сумма / дубль → в ручную очередь (`status='pending'`), алерт.
6. SPL-токены (USDC): те же шаги по `getParsedTokenAccountsByOwner`, зачисление в актив `USDC`.

**Реорганизации:** если блок откатился (статус `reverted`), зачисление сторнируется
(обратная проводка `deposit_revert`), при недостатке баланса — аккаунт уходит в минус-лок
и тикет поддержки (событие редкое, но обязательное к обработке).

---

## 5. Выводы

```
pending_2fa → pending_approval (сумма ≥ порога) → approved → broadcast → confirmed
                                                  ↘ failed / cancelled
```

1. Пользователь: адрес в whitelist (cooling 24 ч для нового адреса) + фактор `ops` + сумма ≤ лимита.
2. Сервис: списание с баланса (`debit user`, `credit platform:withdrawals_pending`) — атомарно.
3. Аппрув: для сумм ≥ 100 SOL — второй админ (4-глаза); иначе автоаппрув по правилам.
4. Batch: сканер группирует выводы в окно 60 с (до 20 получателей, экономия комиссии), строит
   транзакцию (System program `transfer`), отправляет в crypto-core на подпись.
5. Отправка: `sendTransaction(preflight=true, maxRetries=3)`, затем poll статуса до `confirmed`;
   при `failed` — разбор ошибки (insufficient funds / blockhash expired / priority fee) и retry
   с новым `recentBlockhash` и повышенным priority fee.
6. Итог: `confirmed` ⇒ ledger-проводка `withdraw` в `platform:hot`; уведомление с signature и
   ссылкой на explorer.

**Лимиты:** суточный 50 SOL/пользователь (повышение — поддержка + фактор ops + 24 ч cooldown),
hot-баланс ≤ 500 SOL, при превышении — авто-sweep в cold.

## 6. Сверка (reconciliation)

Ежесуточно (и по требованию в админке):

```
A = Σ ledger-балансы пользователей (SOL)
B = Σ escrow активных заказов
C = hot_wallet_balance (on-chain, getBalance)
D = cold_wallet_balance (on-chain)
E = Σ deposits(confirmed) − Σ withdrawals(confirmed) − Σ fees
Инвариант: A + B == C + D + (временно в пути: broadcast-выводы) ± E_adjustments
```
Расхождение > 0.000001 SOL ⇒ алерт **P1**, автоматическая приостановка выводов, отчёт в админке
с разбивкой по счетам. Дополнительно: раз в час — выборочная сверка 100 случайных
`sol_transactions` с RPC.

## 7. Безопасность ключей

| Мера | MVP | Прод |
|---|---|---|
| Хранение MK_sol | файл 0400, отдельный пользователь, шифрование KEK | HSM/PKCS#11 или cloud KMS |
| Доступ к подписи | service-token + allowlist `purpose` | mTLS + политика Vault + 4-глаза |
| Hot/cold | один hot + «cold» в оффлайн-хранилище | hot (онлайн, лимит) + warm (multisig) + cold (оффлайн, ceremony) |
| Multisig | — | Squads/Realms 3-из-5 для cold и критичных операций |
| Ротация | 365 дней | 180 дней + после любого инцидента |
| Мониторинг | метрики подписей, алерт на аномалию | + поведенческий анализ, geo-fence для подписантов |

## 8. Операционные сценарии

* **RPC деградировал**: переключение на резервный провайдер; если оба недоступны — депозиты
  накапливаются в очереди (`seen`), выводы ставятся в `approved` и ждут; UI показывает баннер
  «Сеть Solana: задержки зачисления».
* **Компрометация hot-кошелька**: немедленный sweep остатка в cold (через резервный путь),
  остановка выводов, ротация MK, пересчёт адресов (новые индексы), коммуникация, постмортем,
  компенсационный фонд (резерв площадки).
* **Спам-транзакции/dust-атака**: фильтр минимальной суммы (0.01 SOL), dust объединяется
  при sweep, не отображается в балансе до порога.
* **Санкционные адреса**: проверка получателя по blacklist (OFAC-списки, обновляются в админке);
  совпадение ⇒ отказ и тикет.

## 9. Развитие: некастодиальный эскроу (этап 5+)

Для снижения риска R1 предусмотрен переход на on-chain эскроу без изменения API:

* Anchor-программа `sitee_escrow`: PDA на заказ (`seeds = ["escrow", order_id]`), состояния
  `funded → delivered → released/refunded`, таймер авто-релиза, арбитражный PDA (multisig
  площадки + независимый арбитр, 2-из-3) для спорных случаев;
* покупатель подписывает `deposit`, продавец видит подтверждение on-chain, `release` — по
  подтверждению покупателя или решению арбитра;
* площадка хранит только публичные данные заказа и подпись решения (не хранит ключи пользователей);
* комиссия площадки удерживается в момент `release` (split-instruction);
* миграция: гибридный режим (мелкие суммы — внутренний ledger, крупные — on-chain), затем полный
  переход. Интерфейс `EscrowProvider` в Go уже абстрагирует обе реализации.

## 10. Метрики и алерты

`sol_deposit_confirmations_seconds`, `sol_scanner_lag_slots`, `sol_withdraw_duration_seconds`,
`sol_hot_balance`, `sol_rpc_errors_total{provider}`, `sol_reconcile_diff`,
`sol_sign_requests_total{purpose}`. Алерты: lag > 60 слотов (P2), reconcile diff ≠ 0 (P1),
hot > 80 % лимита (P2), доля failed-выводов > 5 % за 15 мин (P2).
